## 排查「模型和 provider 对不上」（已定位，未修）

结论：**pi.dev 是最新的，不是它的锅**。根因在 `RemoteCatalogProvider.remoteModels():50-62` 的丢弃判定。

- 判定式：`localGeneratedAt !== undefined && (entry.lastModified === undefined || entry.lastModified <= localGeneratedAt) → 返回 []`（整个远程目录被静默丢弃，回退 pi-ai 内置数据）。
- `localGeneratedAt` = pi-ai 0.84.3 包内 `modelDataManifest.generatedAt` = **2026-08-24T10:56:49Z**（写死在包里，升 pi-ai 才会变）。
- 实测 8 个缓存 provider 中 **anthropic（lastModified 08-11）和 openai-codex（08-17）早于 08-24 → 远程目录被丢弃**，实际吃的是 8/24 内置旧数据。
- 上游 pi.dev 全部 provider Last-Modified 均为 2026-09-18 10:44 UTC，ETag 与本地一致（deepseek 实测 304 命中）。
- 差异实锤：anthropic 上游 14 个 vs 缓存 13 个，缺 `claude-fable-5-1`；openai-codex 上游 6 个 vs 缓存 7 个，新增 `gpt-6-astra`、移除 `gpt-5.4`/`gpt-5.4-mini`。
- 陈旧成因：无凭证 provider 不被 refresh（listModels 只取已鉴权、reloadModels 过滤 canRefreshProvider）→ 缓存冻结 → lastModified 越来越旧 → 越容易跌破丢弃阈值。登录后 force 刷新可自愈。
- 另一坑：304 分支（:151-159）只更新 checkedAt、**不更新 lastModified**，该字段会冻结在首次抓取值。
- 深seek 官方 /models 实测与 pi.dev 完全一致（deepseek-flash、deepseek-v4-pro），deepseek 这条线无问题。

## OpenCode Zen「对不上」实锤（18:33 用户截图，已落盘 附件/现场图片/2026-09-19_1833_opencode-zen模型列表截图.png）

根因：**pi.dev 目录 = 平台全量目录（68 个），账号 key 只授权 4 个**，MyBuddy 不做账号级可用性过滤。

- 调用级验证（key=auth.json opencode，base=https://opencode.ai/zen/v1）：
  - 官方 `/v1/models` 只返回 4 个：`deepseek-v4.1-flash`、`muse-spark-1.2-contributor-free`、`muse-spark-1.3-contributor-free`、`test`。
  - `deepseek-v4.1-flash`（官方 id）→ 200 成功。
  - `deepseek-v4-flash`（pi.dev 目录 id）→ `Model access is disabled`（**连 id 都漂移**）。
  - `claude-sonnet-4-6`（目录 68 个之一）→ `Model access is disabled`。
- 即 MyBuddy UI 列出 opencode 68 个模型，其中 64 个选了就报错；官网定价表（用户截图）也是平台目录价，≠ 账号授权。
- opencode-go（baseUrl /zen/go/v1）24 个目录模型，账号实际可用集未验证，大概率同样对不上。
- 潜在修复路径（未实施）：models.json 给 opencode 配 `modelDiscovery:{mode:"openai-compatible"}` 强制拉官方 /models（composeProvider 的 useCustomDiscovery 分支）；或 runtime 加账号级 /models probe 过滤；或短期用 disabledModelIds 手动禁用。

### 不改代码即可根治的原理（代码读通，未落地）
代码里**已存在**账号级 /models probe（`CustomModelDiscovery.discoverCustomProvider`），原本只服务自定义网关，可对 builtin provider 复用：
1. `composeProvider` 的 `useCustomDiscovery = cfg && canDiscoverCustom(cfg) && (!base || mode === "openai-compatible")` —— builtin（base 存在）时只要 mode 显式写 `openai-compatible` 即命中。
2. `discoverCustomProvider` 是**全量替换**（:103 `ids.map(...)` 返回，非 merge），不是叠加。
3. `getConfiguredModels()` 的 seed = `discoveredModels ?? rawBaseModels()` —— discovery 一旦成功，pi.dev 那 68 个（rawBaseModels）根本不进 seed；且 `provider.getModels = getConfiguredModels`（:275）绕开了 withRemoteCatalog 的 mergeModels，所以 overlay 不会叠回。
4. endpoint 默认推导 `${baseUrl}/models`；`requestHeaders` 用 context.credential 的 api_key（需已认证）。
- 坑：discovery 的 persist 只写 `{models, checkedAt}`（无 etag/lastModified），会覆盖 pi.dev 缓存 entry；新 id 元数据走 fallback（`baseline.find(api===config.api)` 继承 contextWindow/maxTokens，reasoning 判 false），需在 models.json 的 `models[]` 里显式补正。
- 代码级方案（对比）才是动 MyBuddyModelRuntime：把 useCustomDiscovery 的门槛从 `mode==="openai-compatible"` 放宽、或给所有 builtin 在 refresh 后统一加 probe+filter。
- 连带效果（好）：`nativeRefresh` 判据含 `mode !== "openai-compatible"`，故配成该 mode 后 pi.dev remote catalog 刷新被整个关闭，68 个不会回流。
- 残留：首帧/离线仍可能是 stored 里的旧 68 个，需联网成功刷新一次才稳定；`test` 与 `muse-spark-*-contributor-free` 会进列表（删除需走 disabledModelIds，models[] 只能改元数据不能删）。

## 架构 review：要不要自研 provider 层摆脱 pi？（19:53，只读结论）

**依赖面积实测（很窄）**：全仓仅 6 个文件 import `@earendil-works/pi-ai`，共 11 处。
MyBuddyModelRuntime.ts(4)、pi-bundled-runtime.ts(3)、extension-model-registry.ts、RemoteCatalogProvider.ts、PiDependencyAudit.ts、CustomModelDiscovery.ts 各 1。

**pi-ai 承担的工作量**：5.9M / 744 文件 / `dist/providers/data/*.json` 39 个内置 provider。
MyBuddy 用到：builtinProviders、createModels、JsonCredentialStore、JsonModelsStore、
getApiProvider、registerBuiltInApiProviders、getBuiltinModelDataGeneratedAt，以及 AssistantMessageEventStream 类型。
另有 `@earendil-works/pi-ai/bun-oauth`（OAuth 流程）+ `/bedrock-provider`（Bedrock）经 pi-bundled-runtime.ts 静态注册（Electron 打包不能用变量 specifier 动态 import）。

**项目自带退役框架**：`src/shared/backend-retirement.ts`（334 行，去 Pi 中心化 Stage 5）定义 5 个选项
keep / keep_pi_ai_only / acp_merge / remove_runtime / replace_provider。
`replace_provider`（= 自研 provider 层）在 :297-299 被**硬编码 executableNow:false / targetState:false**，
blocker 写死为「provider adapter 覆盖评估数据不足」。即项目方法论自己判定：现在不能自研。
`PiDependencyAudit.ts` 的 RETIRED_PACKAGES 只含 pi-coding-agent / pi-agent-core / pi-tui，
注释明示「@earendil-works/pi-ai 是保留的 provider SDK，计 records 不计违规」。

**结论立场**：分层看——
- 目录/发现层（pi.dev）→ 可且值得脱钩：外部网络依赖 + 不可控数据源（id 漂移、账号授权缺失都源于此），已有 `catalogBaseUrl` 参数可换源。
- 协议执行层（pi-ai）→ 保留：39 家协议适配 + compat 细节 + OAuth + Bedrock，自研是长期维护负担。
- 中间路线即 `keep_pi_ai_only`。
- 解锁自研的唯一钥匙：先产出 pi-ai 的 provider 覆盖评估数据（代码里写死的 blocker）。
