# 缓存策略评估：真实文件任务与生命周期边界

本文件保留实现前的方案评估；后续正式实现及验收见 [增量证据实现报告](../context-ledger-acceptance.md)。下文“本轮”指当时的评估阶段。

本轮是方案评估和实验原型，不是生产实现。没有改动 `src/`，没有替换桌面安装包。

## 测试口径

- 真实模型：本机 MyBuddy 已配置的 Magpie `codex/gpt-6.1-terra`，没有切换供应商或模型。
- 真实操作：模型读取 CSV，编写 `calibrate.mjs`，通过 Node 执行，再读取实际生成的 JSON；宿主用独立算法检查 6 个字段。输入是专门生成的非敏感工程数据，不是用户正在进行的任务。
- 第 1 轮建立程序与规则 v1；第 2 轮替换数据，规则不变；第 3 轮更新为 v2；第 4 轮释放并重新打开同一会话，继续处理新数据。
- 原始 CSV 分别有 161/162/163/164 条记录，gain/offset 从 2/+7 改为 3/-4。校验 count、rawTotal、convertedTotal、gain、offset、revision。
- 请求观测发生在供应商序列化器的 `onPayload`，比较完整历史 input 的逐项哈希以及全部非 input 字段，缓存键只保存哈希。不修改被观测的请求。
- 每个请求的响应流单独关联自己的 usage/responseId，避免压缩请求插入后按数组下标错配。另按响应 ID 哈希关联本地网关 usage/routing，只导出元数据。
- 离线测试使用真实 Pi 会话、工具与 Responses 序列化器，禁止联网，覆盖更新、重新打开、原生压缩、引用损坏和发送前撤销。离线 usage 全为零，不能拿来计算命中率。

## 先修正之前的解释

1. “只在首轮注入，损失为零”不成立：首轮有胶囊、第二轮删除胶囊，第二轮仍破坏一次前缀。
2. 稳定前缀使缓存可复用，不保证 100% 命中。相同客户端前缀、同一可见网关账号，也可能遇到供应商内部变化；本轮没有供应商内部证据去区分淘汰、路由、写入延迟等原因。
3. 旧 live 脚本记录的是序列化前 Context，不是完整 payload；工具激活案例实际没有改变工具集。旧统计不能证明该案例的缓存下降由工具激活引起。
4. “只在请求中投放”不代表事实从不落盘：助手回答、工具参数、输出代码、工具结果和摘要都可能包含派生事实。
5. 旧历史命中率比较混合了任务、模型、时间和应用版本。它们是排查线索，不能直接当成某方案造成的计费损失。

## 三种原方案的评价

### 一：首轮投放或按长度停止投放

本轮测试了明确可复现的“只在首轮投放”，没有把任意 token 阈值当成验证过的产品策略。

第二轮删除首轮胶囊时发生一次前缀变化；以后可恢复稳定，但最新资料需要通过检索工具补齐。本轮给所有方案相同的检索能力，所以文件任务可以继续正确完成；这不能证明关闭自动召回后所有真实任务的质量都保持不变。

另一个实现细节：`enabled()` 仅控制 Memory 的召回，不能单独关闭 `supplementalEvidence()` 的项目、资料库等来源。直接把 enabled 改成“仅首轮”不足以实现整个方案。

结论：可以作为明确的产品选择或降级，不能作为默认性能修复。

### 二：每轮保存完整证据到会话

Pi 的 `before_agent_start` 支持把隐藏的 custom message 插在用户消息之后，并由原生会话机制落盘。本轮用这一接口，没有直接改写 agent.state。

普通继续、资料更新、重新打开都能保持历史前缀。四轮会保存四份完整快照，即使其中只有两次实际资料版本变化。

代价是会话正文持久化、重复内容和撤销清理。`display:false` 只是渲染选项，不等于加密或禁止导出；没有必要把内部证据混进用户原始指令正文。

结论：技术路径直接，但每轮保存完整快照没有必要；若接受持久化，应采用增量。

### 三：内存中保留历史胶囊并逐字回放

前三轮能保持前缀，重新打开会话后内存状态消失，旧胶囊不能还原，第四轮发生变化。完整回放同样重复保存未变化的证据。

它也不应实现为逐轮淘汰的“环形窗口”：每淘汰一次早期胶囊都会重新制造缓存变化。应把生命周期绑定到原生压缩边界，并在压缩后重新建立当前版本；不能只沿用“已发送过版本”的去重状态，否则会误以为模型仍能看见已经被压缩掉的证据。

结论：适合作为不额外持久化正文的中间方案，但必须接受重启损失，或增加可恢复的版本引用。

## 新方案

### 四：只追加变化的来源版本

以来源身份、版本、实际渲染内容哈希为键。内容不变就不重复投放；内容变化时在新轮末尾追加新版本，旧版本标为历史，明确新版本优先。若原文已有版本，不应使用当前时间、随机 ID、相对时间描述来替代稳定版本。

离线对照中四轮、两次规则版本，完整快照数量为 4，增量为 2。内存增量仍在重新打开时丢失；持久化增量可恢复。不同来源、权限范围和分支必须分开处理，不能因为文字相同就跨来源共用。

单纯“不重复正文”仍有一个模型语义问题：模型不知道上轮版本是否在本轮仍有效。因此可以在当前轮追加一条极短的版本清单，表示当前可用来源及其版本；这条清单在各自的用户轮中保持位置，之后也不移除。该做法已经包含在下一种原型里。

### 五：持久化版本引用，正文按权限还原（本轮优先候选）

会话只保存元数据：来源、版本、原始用户条目锚点、内容哈希、渲染器版本。请求时从可追溯的资料源还原被选中的证据，在原位置逐字回放；新轮追加简短当前版本清单，变化时才追加新正文。

这样既能在重新打开后还原旧前缀，又不用每轮复制整个证据块。本轮原型能从受控来源获取 v1/v2，重新打开后逐字还原，并验证了内容哈希不匹配、未知渲染版本和缺失历史版本时拒绝还原。

上线前的实际约束：

- `MemoryService.history()` 能读取历史版本；调用前仍必须检查当前访问范围及撤销状态。版本存在不等于仍有访问权。
- 当前项目/资料库投影常用 `updatedAt`、项目版本表示当前状态；版本标识本身并不保证旧正文可以取回。必须逐种来源确认不可变历史能力。
- 召回排序、选中的片段范围、预算截断和模板渲染也影响字节。只保存 sourceId/revision 不一定足够，必须保存稳定的选择和渲染信息，并用哈希拒绝静默变化。
- 原版本缺失、权限撤销、渲染不兼容时，应明确重建有效上下文；不能拿当前正文冒充历史版本以保缓存。
- 引用 ID 和版本元数据本身也有隐私含义。没有写完整胶囊不等于不会留下派生事实。

结论：适合有不可变历史的 Memory 来源；不能未经验证就扩到所有项目、资料库和外部内容。

### 六：固定检索工具，按需读取

工具定义保持稳定。模型需要资料时调用检索工具；工具结果正常追加到会话，天然参与下一次请求前缀。无需自动重复注入整个记忆块。

代价是召回可靠性和工具往返：模型必须知道何时检查最新规则；本轮任务提示明确要求当前校准，因此是有利场景，不能代表模糊任务的自发召回水平。检索结果也会进入原生会话历史，因此此方案不是“正文永不落盘”的隐私替代。

结论：适合大篇幅资料和偶发事实，与小型稳定约束/版本清单组合使用。

## 撤销和压缩的关键边界

原型的发送前 guard 能在来源撤销后拒绝请求，验证结果是“没有新的网络发送”，并不是“删除了全部影响”。离线原生压缩的摘要故意保留旧事实，以证明只移除胶囊不能清除摘要里的派生内容。

正确的生产设计需要定义撤销的语义，关联原始证据、摘要与派生上下文；必要时新建受控上下文，接受一次缓存重建。权限与撤销优先于缓存命中率。测试没有提供生产级派生事实擦除实现。

## 本轮实测结果

9 种策略共完成 11 组实测（当前方案与版本引用各重复一次、交换先后顺序），187 次真实模型请求，44/44 份结果正确。每组是 4 轮、17 次请求。以下命中率含冷启动和新文件内容，只是观察值，不是计费节省的因果估计。

| 策略 | 每组客户端前缀改写次数 | 观察命中率 | 额外记忆检索次数/组 | 关键取舍 |
| --- | ---: | ---: | ---: | --- |
| 当前逐轮替换胶囊 | 3 | 79.4%、81.2% | 0 | 每个新用户轮都有结构性变化 |
| 只在首轮投放 | 1 | 83.2% | 3 | 第二轮删除胶囊；后续更新靠检索 |
| 每轮完整快照落盘 | 0 | 88.7% | 0 | 四轮存四份快照 |
| 内存完整回放 | 1 | 88.9% | 0 | 重新打开丢失回放记录 |
| 内存增量 | 1 | 84.1% | 1 | 减少重复，仍有重启边界 |
| 持久化增量 | 0 | 83.2% | 2 | 不重复原文，但未经本轮确认时模型仍会查新版本 |
| 版本引用＋增量＋短清单 | 0 | 92.6%、87.7% | 0 | 需可重建的历史版本和稳定渲染 |
| 按需检索 | 0 | 90.5% | 4 | 最新资料获取可靠性依赖检索行为；结果进入历史 |
| 冻结首个快照 | 1 | 77.4% | 2 | 快照在第三轮过时，模型通过检索补救；重启仍变前缀 |

这些任务给所有策略同样的检索工具。冻结快照和首轮投放之所以仍然算对，不是因为旧快照自动更新，而是模型通过检索得到了 v2。也没有观察到按需检索必然多一次模型请求：此任务允许它与读文件并行，所有组仍为 17 次请求。更复杂任务的额外往返需要另外测量。

当前方案两次复测的后三轮开头，缓存读取均回到 4224 token。版本引用第一次对应未缓存输入为 216/281/267 token；复测为 327/6531/243，其中中间那次客户端 input 完整保留、非 input 字段也未变化，却仍只读到 4224 token。该异常不能归因于胶囊位置变化，网关后续转换与供应商内部缓存行为尚未定位。

本机网关记录按响应 ID 哈希逐条核对；具体关联和尝试次数见 [summary.json](summary.json)。同一可见账号与一次 HTTP 尝试不等于供应商内部缓存分片也相同。

## 建议

优先选择“按来源版本去重，追加增量”。小型高价值约束保留稳定版本清单；大篇资料按需检索。有不可变历史的来源可使用版本引用恢复，不具备历史能力的来源不能假装恢复旧前缀，应选择明确的持久化快照或接受重新打开时一次上下文重建。

不建议默认关闭长任务的记忆，也不建议每轮保存整个胶囊。短期可使用内存增量并明确重启边界；要解决重启后复用，再落地版本引用。产品实现还需覆盖真实 Memory Kernel、所有资料来源、分支切换和撤销后的派生上下文处理。

## 检查结果

- 9 种策略离线行为测试通过；内容哈希损坏、渲染器版本不支持、历史版本不存在均拒绝还原。
- 原生压缩后重新建立当前证据；摘要保留旧事实的反例已验证。
- 发送前撤销 guard 拒绝请求，离线网络尝试为零。它只是原型发送门禁，不是生产级清除实现。
- 类型检查棘轮通过，无新增错误。
- `test:all` 第一次有 8 项收到 Windows 中断信号；逐项重跑全部通过，再次完整运行 **251/251 通过、0 失败**。没有更新失败基线。

## 可复跑的入口

```bash
pnpm -s test:cache-strategies
MYBUDDY_CACHE_EVALUATE_LIVE=1 pnpm -s cache:evaluate
node scripts/cache-strategy-report.mjs
```

可用 `MYBUDDY_CACHE_STRATEGIES=current,refs` 选择场景。live 每个场景最多 45 次调用、每轮 150 秒，来源数据和写入目录都隔离。每次结果写入独立时间目录，避免覆盖先前证据；离线输出在 `out/diagnostics/`。

原型只是对目标机制的最小实现，尚未加入完整 Memory Kernel、桌面 AgentService、权限切换、会话分支和每一种来源的生命周期。因此本轮可以用于选择架构，不能替代产品上线验收。
