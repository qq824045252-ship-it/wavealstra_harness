# 示波器 / 频谱仪真实任务缓存审计

快照截止：2026-11-03 17:32:30（北京时间）。这是对用户真实任务的只读诊断，不是合成任务结果。

## 结论

旧版有明显的跨用户轮缓存读取量反复退回固定位置的现象。旧代码在下一轮不再回放上一轮的临时证据、改在当前用户消息之后插入新胶囊；实际用量规律、Memory 创建时序与此前真实序列化实验共同支持这一主要解释。由于历史完整请求未留存，不能逐字确定这两个任务每次请求的首个差异。

包含新证据账本的 0.1.79 已出现两次跨轮首请求高命中的自然样本，但仍出现一次轮内骤降。**目前不能将“跨轮实现通过回归”等同于“真实任务的所有缓存异常已修复”。**

## 数据与口径

- 示波器：`local-1793687588697-0`，旧版 107 条主会话模型回复、18 个用户轮。
- 频谱仪：`local-1793692092906-37`，旧版 75 条主会话模型回复、12 个用户轮；另固定截取新版 27 条回复（#76–#102，第 13–15 轮）。第 15 轮在截取时尚未结束。
- 来源：只读 `app.db`、两项任务的 Pi session JSONL、Magpie `usage.jsonl` / `routing/2026-11-03.jsonl`、主进程启动日志。没有读取/修改任务源代码或操作运行中的用户程序。
- **209/209** 条回复通过 response ID 与网关用量唯一对应，未缓存输入和缓存读取数逐条相等。统计仅含主会话，不含子代理的模型调用。
- 所有最终用量记录为 HTTP 200、同一可见账户、同一实际模型 `gpt-6.1-terra`。这不证明上游内部缓存节点一致。
- #82（频谱仪新版）有同账户的 502 → 200 两次路由尝试，最终命中 99.8%；另外部分请求有两次网络发送。因此不能把“最终 200”误解成“没有传输异常”，也不能把多次发送本身认定为缓存下降的原因。
- 命中率 = `cacheRead / (input + cacheRead + cacheWrite)`；这里 `input` 是未缓存输入。本快照的 cacheWrite 均为 0。
- 可复核的逐请求数值：[usage-snapshot.json](usage-snapshot.json)。不包含凭据、请求正文或原始账户标识。

## 旧版的跨轮规律

从第 2 到第 11 用户轮，每一轮首请求的缓存读取均为 **24,704 tokens**：

| 2 | 4 | 41,065 | 24,704 | 60.2% |
| 3 | 7 | 44,373 | 24,704 | 55.7% |
| 4 | 13 | 54,244 | 24,704 | 45.5% |

这解释了讨论任务的体验：很多讨论轮只有一次模型调用，该轮没有后续工具调用把命中率拉回来。相反，一轮执行很多工具时，后续请求通常能复用当轮上下文。

旧版 75 次请求的输入 token 加权平均为 **87.5%**；只看 12 个用户轮的首请求为 **27.5%**（包含首次冷启动和一次重开归零），其余轮内请求为 **96.3%**。主界面的 `contextCacheHitRate` 来自主会话累计 token 比例，因此累计值会掩盖逐轮首请求的问题；不是比例公式计算错误。

### 示波器

前期多数新轮首请求超过 98%。第 13 轮开始后的多次跨轮读取退回 **55,808 tokens**：

- #42：99.8%；下一轮 #43：70.6%，缓存读取由 79,232 退至 55,808。
- #70：99.5%；下一轮 #71：50.7%，缓存读取由 109,056 退至 55,808。
- #72 仍只有 49.2%，#73 恢复到 99.4%。#72 是轮内异常，不能仅用“新用户轮”解释。
- 后续 #79 为 0%，#80 恢复到 99.7%；#95 又降到 18.8%。最后几次已恢复到 99% 以上，所以后期下降具有阶段性。

整段输入 token 加权平均 **94.8%**；首请求合计 **77.8%**，其余轮内请求 **97.0%**。

### 与实现及 Memory 时序的对应

0.1.75 的 `EphemeralContextProjection` 在 `message_start(user)` 和 `agent_settled` 清除临时胶囊；`context` 从原生消息构建投影，只在当前用户条目之后插入一个胶囊。旧胶囊未写入会话，因此下一轮不再占据旧位置，即使来源正文没变也会改变历史请求前缀。

示波器任务的首条任务来源 Memory 决策创建于 **15:11:27**，紧接着 **15:12:07** 开始第 13 轮。此前首请求大多高命中，后续跨轮出现 55,808 的重复截点。频谱仪从 **15:48** 开始时，这条同空间 Memory 已存在。此时序与“前一个任务晚些时候开始注入，后一个任务从开头就注入”的解释吻合，但数据库中存在 Memory 并不能单独证明某次召回的精确正文。

两个旧版会话没有原生 compaction 记录，`model_change` 记录重复的是同一个模型，不能当成实际换模。

| 任务 / 请求 | 北京时间 | 表现 | 可确认的边界 |
| --- | --- | --- | --- |
| 示波器 #79 | 15:37 | 0%，下一次 99.7% | 新用户轮；未发现同时间应用重启；具体原因未定 |
| 示波器 #95 | 15:41 | 18.8%，只读 25,728 缓存 tokens | 同一轮，前一工具是 Go 测试/构建；无原生压缩；单次路由/网络发送 |
| 频谱仪 #54 | 16:40 | 0%，下一次 99.9% | 16:40:18 有 0.1.75 启动记录，首请求于 16:40:50 发出；距上一模型请求约 11 分钟；重开及闲置因素叠加 |
| 频谱仪 #62 | 16:46 | 18.3%，只读 25,728 缓存 tokens | 同一轮，前一工具是 Go 测试；一次路由、两次网络发送；未证实因果 |

#95 的报告输入合计从上一请求的 139,621 降到 136,504；新版 #84 从 162,856 降到 158,677。**token 数减少不等价于客户端删除了消息**：没有历史最终 payload，无法区分客户端转换、网关转换、图片/推理历史处理及上游缓存行为。

## 下一步诊断所需证据

轮内异常尚未定位。进一步验收应增加实际供应商序列化后的请求指纹：逐 input 条目哈希、非 input 顶层参数哈希、工具 schema、会话/cache key 哈希、账本/压缩边界，以及 response ID 对应关系。只记录必要元数据，不落凭据和完整正文。

复现应覆盖这次真实工作负载中的 13–18 万 token、图片、推理历史和普通工具返回后的连续请求。客户端最终 payload 稳定时再向网关转换及上游缓存定位；客户端发生变化时，依据首个差异定位具体转换。现有历史计数不足以替代这些证据，也不足以承诺消除全部缓存骤降。
