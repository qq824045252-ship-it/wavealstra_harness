## 图片和搜索之后实际发生了什么

- 示波器 #36 发起首个截图时读缓存 74,112 tokens，命中 99.4%；#37 收到该截图后读缓存 74,496 tokens，命中 97.5%；#38 再收到一张截图后读缓存 76,160 tokens，命中 97.3%。缓存历史没有表现为“遇到图片即清空”。
- 频谱仪 #16 发起首个截图时读缓存 54,784 tokens，命中 99.0%；#17 收到后读缓存 55,296 tokens，命中 96.7%。
- 两个首图都是 JPEG 图片块，图片字节分别 50,581、54,045；Base64 字符数分别 67,444、72,060。相伴文字结果仅 2,508、2,504 字符，无法容纳整张 Base64 的重复文本。Base64 是传输编码，不能按字符数直接推算视觉 tokens。
- 频谱仪最大 subagent 结果来自 #38，后续 #39 命中 97.6%。示波器最大结果来自 #71，后续 #72 仅 49.2%，但此前 #71 已是 50.7%，两者都停在 55,808 个缓存 tokens；#73 恢复 99.4%。后者仍需解释，不能被包装为“所有子代理输出都不可缓存”，也不能凭相邻关系认定因果。

## 应如何解释

新截图、动态网页结果、包含随机目录的命令输出，都可以作为新的尾部消息出现。它们本次产生新输入，但一旦成为不变历史，后续请求仍可复用此前前缀。真正需要排查的是旧消息被删掉、改写、重排、重新缩放/编码，或工具/系统参数改变，以及客户端外的缓存行为。

子代理拥有独立调用链。主会话指标不包含其内部请求；全局网关统计则可能包含它们。这是统计口径问题，不能证明主会话历史被破坏。

旧版每轮移除上一轮临时证据的机制，能同时解释截图前就出现的固定缓存截止点，以及随着上下文增长而下降的首请求百分比。0.1.79 的增量账本把已经发送的证据和版本清单固定在原锚点；新变化只追加。来源哈希不是供应商缓存键，看到新哈希本身不能判定旧前缀变了。把同一动态块在每次请求中反复挪到最末尾会重排历史，不应这样处理。

这些记录否定了粘贴分析中的若干断点和必然性结论，但没有补出历史最终 HTTP 请求。新版 #84 的轮内骤降仍未定位。0.1.81 的序列化/HTTP 指纹用于在下一次事件中区分客户端输入变化与客户端之外的因素。
