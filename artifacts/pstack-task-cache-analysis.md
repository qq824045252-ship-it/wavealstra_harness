# pstack 实施任务的缓存读取分析

缓存整体有效。主代理输入的 97.74% 来自缓存，包含子代理和可观测附加调用后的加权比例为 95.38%。高命中率不等于任务执行高效，两个缓存表现良好的 scout 仍超时退出。

## 统计范围与口径

任务为 `local-1793848170484-0`，会话为 `01a1a9ae-daf4-774e-94f0-00e5307f170f`。统计从 2026-11-05 11:09:31 开始，到你提出缓存分析问题之前截止，即北京时间 12:35:14.630。不包括本轮分析产生的调用，也不包括之后发生的第二次上下文压缩。

采用 Explain the Number 原则。先区分输入总量、累计缓存读取和单次命中率，再将错误与压缩开销分开统计。

命中率采用 `sum(cacheRead) / sum(input + cacheRead + cacheWrite)`。这里的 `input` 是未缓存输入，不包含已计入 `cacheRead` 的部分。输出 token 不进入分母，单次命中率也不直接取平均。所有记录的 `cacheWrite` 都为 0，这不代表服务端没有建立缓存。

主代理有 127 条正用量响应和 1 条 WebSocket 错误。错误记录的 token 全为零，不能将它画成一次 0% 命中的成功响应。额外 prompt 调用发生在最终答复后，只有一个输入 item，未进入对话记录，其具体业务用途未确认，所以单独列出。

累计读取的 2,395.7 万缓存 token 是多次请求的加总，不是单个上下文的长度，也不是互不重复的内容。费用字段不是账单，本报告不据此估算实际支出或节省金额。

### 压缩导致的下降有明确依据

11:56:51 的 compaction 记录显示，压缩前上下文估计为 218,050 token。主请求输入从第 58 次的 216,874 缩小到第 59 次的 56,002 token。

provider 层指纹也显示输入 item 从 164 减至 37，首条历史内容被摘要替换。这解释了缓存读取从 215,168 降到 28,160。不能将被删去的历史全部算作缓存损失，它们已经不再发送。

### WebSocket 错误后的下降值得单独调查

第 114 次请求出现 WebSocket 错误。紧接着的 `context_edit` 移除了这个失败的 assistant 条目。第 115 次重试与失败请求的 provider 层 bodyHash、modelHash 相同，211 个输入 item 全部一致。

因此，没有证据证明这次下降是应用层重新排列旧历史造成的。第 115 次的 98,172 个未缓存输入占主代理全部未缓存输入的 23.19%。这是集中异常，不是整个任务反复掉缓存。

但这仍不能证明上游缓存故障。主链没有完整的最终传输正文观测，重试后的 HTTP 记录标记为 `unsupported-or-over-limit`，此前主要走 WebSocket。已有证据只能把异常定位到 WebSocket 错误及后续传输恢复附近，不能区分最终序列化差异、连接关联、上游路由或缓存放置。

## 判断与优先级

这份记录不支持“缓存持续失效”的判断。主链 provider 层除了自动压缩，没有发现其他前缀断裂；大部分正常调用的命中率接近 99%。这只是应用层指纹结论，不等于最终传输层或上游正文已被验证一致。

更有价值的后续方向是限制无结果的子代理运行、缩小委派范围，并补全 WebSocket 恢复时的脱敏请求指纹。不要为了保住命中率而禁止必要压缩，也不要把大量缓存读取当成零成本。
