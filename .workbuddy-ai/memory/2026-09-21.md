### 被推翻 / 更正的事实
- **Policy 链路顺序说反**：Permission 扩展注册在 ECP **之后**（`SessionExtensionAssembler.ts:185-203`），非提案所述之前。
- **TaskWriteAuthorizationService 不是链路节点**，是注入 Guard/ECP 的共享协作者（S:176-183/218/252）。
- **ECP 扩展无 tool_call handler**（N:486 由 execute 包裹）。
- Project 工具实际 **+27** 而非 +22。

### 评审新发现的 🔴（提案未写）
- `NativeExtensionRuntime.ts:348` `this.handlers.get("tool_call") ?? []` → handler 缺席则整链不执行、工具照跑。**fail-open，非顺序问题**。PDP 须由 runtime 无条件调用且 fail-closed。
- `TaskWriteAuthorizationService.consume(:110)` 只比 (toolCallId, rawPath)，不查 permissionMode；`grantedExternalWriteToolCalls` 无 TTL；`SessionApprovalBridge:128` 命中即 true → 永久授权。真问题是**绑定维度不足**，非竞态（Node 单线程，同步 get+delete 无 TOCTOU）。

### 关键架构事实（后续复用）
- 真正耦合面在 **src/shared DTO**：AssemblyTraceDto 11 文件、RuntimeContextSnapshot 10、AssemblySegment 7、Loadout 5 —— 改 DTO 一次打穿 main+shared+renderer+33 个测试脚本（约 1207 assert）。src/main 直接 import 反而很少。
- Trace 不用新建：`RuntimeContextSnapshotRepository`（`AgentService.ts:3803` 每轮已写 assemblyHash/instructions/capabilities），只需给 SnapshotRow 加 providerRequestHash + toolBytes。
- `PromptContextFormatter.ts` 顺序 bug 最小修复：把 84-93 的 UNTRUSTED 声明块整体移到 69 行 excerpt 之前，并修正 :78/:92 方位描述。
- 隐性耦合：Loadout 收窄改 skillCatalog 段（P:475）直接击穿 prompt-cache 稳定前缀；session 重建重置 evidenceByExecution（C:188-206）并触发 usageStats.backfillSession；MCP build 期一次性注册（S:280）重建即冷启动；role=context→user 使 compaction 回填以"用户说的"身份进 provider。

### 主理人收口（成员结论冲突）
- ④ 拆 PromptAssembly 拆为 **④a 结构瘦身**（可立即并行）+ **④b 策略语义外迁**（必须晚于 PDP 建成并 fail-closed）。产品评审员说"可提前"、安全官说"必须靠后"，指的是不同部分。
- "注册顺序 = 权限语义"判定为**被夸大**：N:354 仅 block===true 才 return，是 AND 语义，顺序只影响哪个 veto 先命中。真问题是 handler 缺席。

### 主理人亲自读码复核（重要修正）
- `NativeExtensionRuntime.ts:348` fail-open **维持 🔴**（唯一确认的 🔴）：`?? []` 使 handler 缺席时循环体不执行，直接走 `:358` 后执行；`:354` 仅 block===true return。
- 安全官 F2 **降级 🟡**：`task-workspace-guard-extension.ts:110-113` consume 是 `get 后 delete`（一次性）、rawPath 不符返回 null 且销毁授权、`:117` prune 5min TTL；且 `authorize:81-90` **已做 permissionMode 校验**（readonly 拒绝 / auto 放行 / 其余弹窗）。真实残留风险仅"降级窗口"，极窄。
- **新发现**：`authorize(..., remember=false)` 默认不记住。全库仅 `task-workspace-guard-extension.ts:151`（fs_write）传 true；`execution-extension.ts:208/351` 不传 → 恒走全量 authorize。即**双弹窗抑制实际只对 fs_write 生效**。
- `SessionRegistry.ts:62` 注释证实 `grantedExternalWriteToolCalls` 是"避免双弹窗"的 **UX 机制**，非安全机制。
