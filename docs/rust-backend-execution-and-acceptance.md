| 最终目标 | Rust 管应用后台；Electron 管渲染及必要的平台代理；Pi 保留 Node，并成为独立执行宿主 |

| 执行纪律 | 严格按步骤 1→10 推进；前一步出口门禁通过并留下证据，才能切换下一步的生产所有权 |

**先冻结基线与所有权，再验收现有三条基础契约；然后建立执行桥和后台生命周期，收拢应用数据写入，依次迁 Work、触发与渠道服务、Gadget；最后迁出 Pi Node 宿主，收薄 Electron Main，完成双平台整体验收。**

这里的“Pi 最后”指最后迁移的业务执行宿主。删除过渡适配、完成 Electron 收尾和整体验收必须在 Pi 拆分之后。不得一边把 Pi 留在 Main，一边宣布 Main 已经只负责界面。

## 1. 当前基线与最终职责

### 1.1 已有能力及其边界

| 当前已有能力 | 可以据此确认 | 还不能据此确认 |
| --- | --- | --- |
| `AppDatabase.open(... runtimeAuditSupervised: true)` 接入 Core socket | 生产启动代码已连接常驻 Rust supervisor/worker | Rust 已负责全部应用后台业务 |
| Rust writer、维护事务仲裁、Work 租约写入 | 已迁 Rust 操作具有写入和调度权限约束 | 整个 `app.db` 已不存在 Node 写入 |
| deadline、cancel/status、持久操作回执 | 已迁请求具备生命周期与未知结果处理 | 所有业务均已实现独立恢复、外部效果严格只发生一次 |
| Core 双锁、代次、不可变二进制与版本切换 | Core 所有权与升级交接有明确边界 | 无 UI 时的完整业务自动拉起、持续运行和崩溃恢复已完成 |
| `--resident-host` 无窗口运行 | Electron 可以作为无窗口业务宿主 | 业务已经脱离 Electron 进程 |
| Pi 被动历史读取走 Rust | 部分只读查询已下沉 | Pi 执行、可写 Durable 存储已经搬进 Rust，或 Pi 已独立成宿主 |

基线证据见 [Rust 核心基础契约补全](reviews/rust-core-contracts-2026-11-25.md)、[生产装配](../src/main/index.ts)、[Work 服务](../src/main/agent/work/WorkService.ts)、[常驻宿主](../src/main/host/ResidentLifecycle.ts)、[Pi 执行](../src/main/agent/durable/DurableBotRuntime.ts)及 [Pi 存储](../src/main/agent/durable/DurableStorage.ts)。

基线报告记录 Linux 下 Rust 27/27、原生集成门禁 15/15 通过。这是该 SHA、该环境下的已有证据；本文件的新增验收场景尚未执行，Windows、GUI 和发行包也不能继承这些通过状态。测试数量以后以实际清单为准。

### 1.2 最终职责表

| 层 / 进程 | 最终负责 | 不得继续持有的职责 |
| --- | --- | --- |
| Electron Renderer | 页面、交互、虚拟列表、局部状态、展示与输入 | 数据库写入、后台定时器和任务真源 |
| Electron 薄 Main / 平台代理 | 窗口、IPC 转发、Chromium/WebContents、浏览器会话、系统凭据代理、通知及桌面能力适配 | Work/Cron/Dots/Gateway 的业务调度、应用数据写库、Gadget 共享 HTTP 宿主、主 Pi 执行 |
| 常驻 Rust Core | 应用域数据、命令与事件、调度、恢复、渠道/后台服务管理、Gadget 共享 Host、资源策略、诊断、执行宿主管理 | 重写 Pi 内核及其原生可写存储 |
| 独立 Pi Node Host | 当前 Pi 的模型运行、Agent/Durable、上下文压缩、checkpoint、MCP 与原生 Pi 可写存储 | 绕开 Rust 直接写应用域数据库，或恢复另一套 Work/Cron 总调度器 |
| 按需业务后端 | Gadget 声明的 Node/Python/Go/Rust 业务代码及其约定的数据 | 静态 Gadget 为服务页面而各起一个 Node HTTP Host；擅自取得应用调度权 |

边界补充：

1. `app.db` 及应用域状态由 Rust 接管；Pi 的 `durable.sqlite`、原生 journal/checkpoint 等仍由 Pi Node 持有写入权。业务后端明确声明的私有数据库另列清单，不混入应用单写者验收。
2. Chromium 用户目录、浏览器登录态及必须由 Electron/操作系统完成的凭据处理属于平台边界；不因“Rust 化”改变其格式、归属或安全语义。
3. “退出界面后继续运行”首先覆盖不需要桌面/浏览器的任务。需要这些能力时，由 Core 按需请求或唤起平台代理；代理不可用时明确等待或报告能力不可用，不假称动作已执行。
4. Rust 接管管理职责后，确因协议 SDK 等原因保留的 Node 适配服务必须独立、受监督、职责具名；不得保留一个承载全部旧 Main 逻辑的常驻 Node 大宿主来宣布迁移完成。
5. 复用当前架构与依赖；数据库拆分、新数据库引擎或新运行框架不作为本次迁移的前置条件。若出现必要例外，应先记录原因、所有者、生命周期和验收，不在实施中暗中扩大目标。
6. 常驻、自启、注销存活和休眠期间执行分别记录。本文要求在已启用常驻的受支持用户会话中运行与恢复；系统重启后的拉起按已配置的用户登录/服务机制验收，不承诺关机或休眠时仍在执行，也不默认承诺用户注销后跨会话存活。

## 2. 必须遵守的总顺序

| 步骤 | 先做什么 | 完成后才能做什么 | 出口门禁 |
| --- | --- | --- | --- |
| 1 | 固定基线、盘点所有权、记录行为与性能基线 | 开始证明底层契约可作为迁移基础 | 清单无未归属入口；验收环境、场景、预算和证据格式已确定 |
| 2 | 复验并补齐现有三条基础契约 | 扩展 Core 为业务后台 | 真实 Rust/SQLite/进程故障用例通过；Windows/Linux 原生门禁有证据 |
| 3 | 建立领域命令、持久事件、过渡执行桥及后台生命周期 | 把应用写入和调度控制迁入 Rust | 控制路径独立可用；跨连接身份、宿主断连、事件补读与恢复行为明确 |
| 4 | 收拢应用域写入、初始化及事务 | 切换 Work 总调度器 | 生产应用域写入只经过 Rust；跨域事务保持原子；Pi 原生写入边界不变 |
| 5 | 迁移 Work 状态机、调度与恢复 | 迁移所有向 Work 提交任务的触发源 | 只有 Rust 调度；并发、暂停、取消、恢复和去重通过 |
| 6 | 按 Cron→Dots→Gateway→Remote 顺序迁触发和渠道服务 | 收拢 Gadget 与后台资源管理 | 各域在无界面时按持久规则触发、接收、对账并恢复 |
| 7 | 迁 Gadget 共享 Host、按需后端与资源管理 | 开始最后的 Pi 宿主抽离 | 静态 Gadget 无额外 Node HTTP 进程；后端与权限不依赖 UI 连接 |
| 8 | 把 Pi 拆成独立 Node Host，保留 Pi 实现与存储 | 删除 Main 中的业务宿主及过渡执行桥 | 真正停止整个 Electron 业务进程后，非桌面 Pi 任务仍推进；恢复不双执行 |
| 9 | 收薄 Main，完成 UI 重连、页面回收与兼容代码清理 | 做最终双平台全链路验收 | Main 不再拥有业务循环；UI 可断开重连；生产无旧写入/执行回退 |
| 10 | 全量回归、真实性能、Windows/Linux GUI 与发行包验收 | 宣布整体目标完成 | 必需场景全部通过，安装包证据齐全，已知限制明确且不覆盖必需项 |

**可以并行准备不同模块的代码与测试；生产所有权切换和完成判定必须遵守上表顺序。** 每一域切换时，先停止旧入口、排空或记录在途状态，再建立新 owner，最后开放新入口；不能让新旧两套调度器同时运行。

步骤 3～7 期间，主 Pi 仍由 Main 内的过渡适配执行。此时退出整个 Electron 后，Core 可以保存触发、队列与恢复义务，但必须将需要 Pi 的任务标记为执行者不可用/等待恢复；不能提前标记“无 Electron 自主完成 Pi 任务”通过。每个域交权前还须确认其所有跨域依赖已迁入 Core 或已有具名平台代理，不能保留隐藏的 Main 业务回调。

每步只在 `passed` 后解锁下一步。`failed` 先修本步；`blocked` 补环境或依赖；`not-run` 就是未验收。不得以“源码写完”“测试文件存在”或“编译通过”替代出口门禁。

## 3. 分步执行要求

### 步骤 1：固定基线、所有权和验收口径

**进入条件：** 已明确采用本文目标；工作区已有改动和当前任务不会被覆盖。

**必须按这个顺序执行：**

1. 同步并记录实际 `main` SHA、工作区状态、Node/Rust/Pi/Electron 版本及测试分类。本文的旧基线不能自动充当后续新提交的验收证据。
2. 沿生产入口追踪全部业务入口：桌面 IPC、远程入口、Cron、Dots、Gateway、Work、Gadget、Pi 工具、启动恢复、退出清理、数据库重建、安装与更新。
3. 建立所有权清单。每项至少写明“当前执行进程、持久化位置、写入者、定时/恢复入口、目标所有者、迁移步骤、验收 ID”。把 `db.connection`、直接文件写入、timer、spawn、网络 listener 和恢复回调全部归到具名职责；文本检索用于找入口，运行追踪用于确认真实调用。
4. 将现有行为分为“必须保留”“已退役”“明确不在范围”。按当前文档处理已删除的独立 Bot、预算和审批循环，不能从旧 Bot Work Phase 1–5 计划重新引入这些功能。
5. 准备隔离数据、工作区、模型/渠道 fixture、真实平台账户或测试应用；录下第 7 节要求的性能基线和数值预算。

**必须产出：** 所有权清单、调用/进程清单、基线测试报告、性能基线与预算、未覆盖环境清单。集中放在一次验收的证据目录，并与源码 SHA 绑定。

**通过标准：** 生产入口均有目标归属；应用库与 Pi 库明确分开；性能预算为实际数值而非“更快/更省”；现有测试的通过、基线失败和未运行分别记录。

**禁止跨步：** 所有权未盘清之前，不批量将函数改为异步，不以删除 Node 文件数量或增加 Rust 文件数量计算完成率。

### 步骤 2：先把现有三条基础契约验收闭合

**进入条件：** 步骤 1 通过。已完成的修复复用现有实现；只补真实失败和未覆盖项。

**必须按这个顺序执行：**

1. 验写入与权限：普通 writer 与维护事务共用仲裁；Work lease 获取、续租、释放具有身份和失效约束；失去确认后停止授予新执行权。
2. 验请求生命周期：排队截止时间、实际在途槽位、取消/状态独立通道、已知失败和未知结果分类、持久回执恢复、同 ID 防重。
3. 验 Core 所有权：supervisor/worker 双锁、ready 后发布 endpoint、数据库创建/重建守卫、二进制版本交接、迟到 worker 拒绝访问新一代数据库。
4. 在 Windows、Linux 分别跑真实原生门禁；对加锁、文件替换、进程终止、路径和二进制更新的差异留下实测记录。

**通过标准：** 第 5 节 RC-01～RC-05 通过；已配置原生路径时，超时、过载或探测失败不会静默改由 Node 写入。取消请求的确认和实际取消终态必须分别可观察。

**禁止跨步：** 本步失败时继续修基础契约，不顺带迁 Cron、Gateway 或 Pi。Rust 内部写入串行化通过，仍不能标记应用库唯一写入者完成。

### 步骤 3：先建业务协议、执行桥与独立后台生命周期

**进入条件：** 步骤 2 通过。此时 Pi 仍留在原 Main 宿主。

**必须按这个顺序执行：**

1. 定义具名领域命令和查询，不把任意 SQL、JavaScript 回调或完整内存对象作为跨进程 API。固定 command/operation 身份、业务修订号、Core/owner 代次、错误和结果格式；数据库提交与领域事件/outbox 的关系必须明确。
2. 为 UI、执行宿主、后台服务建立有界、可区分的连接/角色与权限生命周期。各连接的回复只交给原连接代次；一条 UI 断开不能替另一宿主取消已接收的后台工作。
3. 建立事件快照与增量订阅：持久游标、序号/代次、重复事件去重、缺口重同步及保留上限。快照携带一致水位，快照与后续订阅之间不得漏事件；事件回放不得变成命令重放。控制、回执、进展流与批量数据不得共享一个可被长操作占满的无界队列。
4. 提供 `submit/status/pause/cancel/resume/reconcile` 等执行适配能力，先建立 Core 持有的执行槽、并发准入、队列上限、owner 代次和持久交接记录。**过渡适配只把执行送到现有 Main 中的 Pi**；Work 调度逻辑不能藏在适配器里。公共执行协议继续保留，Main 本地适配在步骤 8～9 删除。
5. 在真实执行者前先用可控执行 fixture 验证身份、防重与恢复，再接现有 Pi。执行宿主离线时持久排队或标记等待；没有执行者就不能报告运行中/已完成。
6. 为 Core 增加后台启动、停止和恢复策略：不依赖打开 UI 才恢复后台；定义 worker 故障的有界重启、退避、连续失败熔断、诊断和显式恢复。完整 supervisor 被终止或机器重启时，由所声明的平台生命周期机制重新拉起；只有下一次 UI 打开才重建，不算无人值守恢复通过。
7. 将“关闭窗口”“退出界面”“停止助理”“系统重启”“升级”区分为不同操作。后台启停及自启遵循已有用户设置；停止助理后禁止被自动重启策略立即拉起。

**通过标准：** RC-06～RC-08 通过；生产入口使用新协议；UI 与后台身份分离；无 UI 时 Core 能恢复，Pi 暂时离线则诚实等待。明确记录本步尚未完成独立 Pi 运行。

**禁止跨步：** 不能先把 Work scheduler 放进 Rust，再临时发明无身份的执行调用；不能把“Rust 进程仍在”当成“Pi 任务还在执行”。

### 步骤 4：收拢应用域写入和事务

**进入条件：** 步骤 3 通过；领域命令和事件具备稳定身份。

**必须按这个顺序执行：**

1. 按所有权清单逐域迁移。顺序为：应用配置/基础索引→项目/工作区/任务元数据→资料/记忆/产物→Work/Cron/Dots/Gateway/通知等控制数据→剩余启动恢复和维护写入。已在 Rust 的入口做一致性核对，不另做一套实现。
2. 将读改写与其事件/outbox 封成 Rust 领域事务。对于 Main 目前的 `transaction(() => ...)`，先明确整笔业务不变量，再迁事务；禁止拆成若干异步 RPC 后宣称原子性仍在。并发读后写须校验业务修订/预期状态，不能用最后到达覆盖用户的新要求。
3. 业务结果提交后再广播投影；事件写入失败则按事务契约回滚或留下可恢复 outbox。文件状态与 SQL 无法同事务时使用可恢复的分阶段操作和持久回执。
4. 将应用库初始化、当前格式校验、重建和维护入口一并纳入 Rust 所有权。继续遵守当前数据格式策略；读取失败不得当成旧 schema，活 owner 存在时不得清库重建。
5. 每迁一域，关闭该域所有旧写入口，包括 Pi 工具、远程请求、恢复任务和后台定时回调。最终关闭 Main 对应用库的生产写连接；隔离测试中的 Host 实现若保留，必须无法由生产故障触发。
6. 用运行期写入探针/数据库只读约束证明边界；对比迁移前后同夹具的返回值、持久状态、错误分类和事件，不只搜索源码是否包含 `INSERT`。

**通过标准：** RC-09、RC-10 通过；应用域所有生产写入进入 Rust；Pi 原生数据库仍只由 Pi 持有写入权；Node 的 Pi 写入不得被误判为应用域违规。

**允许的过渡状态：** Work/Cron 等业务调度仍暂留 TypeScript，但只能调用 Rust 领域命令。此状态只证明写入收拢，不能标记调度迁移完成。

### 步骤 5：迁 Work 状态机、调度和恢复

**进入条件：** 步骤 4 通过；执行桥和应用域事务可用。

**必须按这个顺序执行：**

1. 先迁 Work 状态变更、输入修订、事件消费、执行意图/outbox 和恢复扫描；保留当前业务身份及因果链。
2. 再迁 tick、watch、超时/到期、并发准入、暂停积压和资源冲突控制；原 lease 语义调整为 Rust 业务 owner 的权威，不保留 Main 的第二份调度权。
3. 接执行桥，先验普通单任务，再验多任务并发、前台插话、长期 watch、修改/暂停/取消与在途结算。
4. 做切换：停止旧 scheduler→处理在途/持久状态→移交 owner→启动 Rust scheduler→确认 Main 不再 tick 或自行恢复任务。
5. 验成果保存、部分成果、自动归档与投递对账；执行结束、验收通过、交付成功分别记录，不因迁移混成一个 completed。

**通过标准：** RC-11～RC-13 通过；同一 Work 只有一个调度者；独立任务可以并发，冲突资源受控；前台请求不等待后台长任务终态；失去 owner 后不再发起新效果。

**禁止跨步：** 租约已经由 Rust 写入不能替代 scheduler 迁移；重启恢复不能重新分配一个身份，把原未知执行再跑一遍。

### 步骤 6：按 Cron→Dots→Gateway→Remote 迁移触发与渠道服务

**进入条件：** 步骤 5 通过。所有触发源必须提交给同一套 Work/执行入口。

**必须按这个顺序执行：**

1. **先 Cron：** 迁计划装载、计时、时区、休眠恢复和错过触发策略。固定 occurrence 身份；重启与时钟跳变不能重复生成同一次任务。
2. **再 Dots：** 迁监控、discovery、待办/委派、结果回流和主动投递的持久控制循环。保持“轻量个人助理、主要通过委派完成工作”的现行边界；需要模型时调用执行桥，不在 Rust 新建另一套 Agent 内核。
3. **再 Gateway：** 迁入站接收、连接重建、去重、会话路由、出站队列和投递回执对账。必须使用当前支持的渠道清单；不恢复已排除的渠道或旧独立 Bot 功能。
4. **再 Remote：** 迁远程服务的后台生命周期、命令路由和事件订阅，复用同一应用权限和结果身份。客户端重连不能重复执行其上一次命令。
5. 最后迁依赖这些服务的通知、关注度/日程重算、启动 catch-up 与退出清理；完成后 Main 不再启动这些循环。

本步内部也逐项过门禁：Cron 通过后才能切换 Dots，Dots 通过后才能切换 Gateway，Gateway 通过后才能切换 Remote；不能四项一起标完成，只提供其中一项的测试。

**通过标准：** RC-14～RC-16 通过；无界面时触发与接收仍有效；执行桥离线时保存义务并显示等待；第三方不支持幂等/回查时保留 unknown，不承诺严格一次投递。

**禁止跨步：** 不允许各渠道自己起一套 scheduler；不能只把表读写搬走，就把网络连接、timer 和恢复责任算作已经迁走。

### 步骤 7：迁 Gadget 共享 Host 和后台资源管理

**进入条件：** 步骤 6 通过；后台 owner、命令与事件边界已经稳定。

Gadget 所依赖的 Artifact/Library/Workspace 等领域命令必须已在 Core；通过 Main 创建成果或写应用数据的隐藏依赖应在切换前移除。执行槽和基础资源准入沿用步骤 3，本步扩展到进程树、Gadget 实例与资源回收。

**必须按这个顺序执行：**

1. 先把静态资源、路由、数据调用与后台执行边界拆开；为静态 Gadget 建立共享 Rust HTTP Host，保留现有页面/SDK 契约。
2. 再迁 Gadget start/stop/restart、健康检查、退出回收和 Node/Python/Go/Rust 后端拉起。静态 Gadget 不启动专属 Node HTTP 进程；有业务后端时只按声明启动需要的进程。
3. 把后台实例的持久操作权限绑定到后台 owner/实例 generation；UI 的临时观察权限继续绑定 UI 连接。**当前“客户端断开即撤销其 Gadget generation”的机制必须按职责拆分，不能让退出 UI 意外撤销仍合法运行的后台实例。**
4. 迁资源登记与限额：实例/进程数、队列、并发、闲置回收、任务工作区及文件资源冲突；文件持久化继续经过已验收的撤销与提交检查。
5. 对依赖 Electron 的浏览器/桌面动作使用平台代理。Core 负责策略、排队与生命周期；代理报告能力、执行结果和失联状态，不能自行重建业务调度。

**通过标准：** RC-17～RC-19 通过；静态 Gadget 数量增长不增加专属 Node HTTP 进程；业务后端可按需启停；退出 UI 不撤销后台合法权限；stop/revoke 后迟到写入被拒绝。

**禁止跨步：** 仅把 `GadgetHost` 改名、仍每个静态应用启动 Node，不算共享 Host 完成。资源回收不能以销毁未保存状态、执行中的后台任务或有用登录态为代价。

### 步骤 8：最后拆出 Pi Node Host

**进入条件：** 步骤 7 通过。应用域存储、业务调度和服务管理已归 Rust；现有 Pi 执行桥已稳定。

**必须按这个顺序执行：**

1. 盘清 `ModelRuntime → DurableBotService → DurableBotRuntime/Harness` 及模型配置、工具、MCP、上下文管理、子代理、原生存储的依赖。版本从当前 pin 读取，不引入旧 Pi 兼容层。
2. 在独立 Node Host 中复用现有 Pi 实现，保持会话、任务、checkpoint、摘要预算、工具声明和可写存储语义。仅为进程边界增加必要适配。
3. 由 Rust 拉起、登记、监测和停止 Pi Host。每个 Pi 存储具有唯一 writer/lease；宿主 pid、存储身份、generation、执行身份共同参与恢复，过期宿主不能重新获得权限。
4. 将 Pi 使用的项目/资料/记忆/任务等应用能力改为 Rust 命令；将浏览器/桌面能力改为平台代理。Pi 原生 Durable 写入留在 Pi，Rust 只按协议读快照/投影。
5. 切换步骤 3 的执行适配，保持 submit 与回执身份连续；清理 Main 中 `ModelRuntime`、`DurableBotService`、Harness 的生产实例。
6. 做真实 Pi 执行的进程终止验收：停止整个 Electron Main 及其 UI，确认 Pi Host 和 Rust 继续推进；再杀 Pi Host、恢复同存储，核对 checkpoint、回执及效果计数。

**通过标准：** RC-20～RC-22 通过；主 Pi 执行 PID 不等于 Electron Main PID；无需桌面能力的任务在无 Electron UI/Main 时继续；崩溃恢复使用原存储与原身份，不能重复外部效果。

**禁止跨步：** 已有子代理 Node worker 不能替代主 Pi Host 验收；把 Pi 的 SQLite 写入挪进 Rust，或重写其压缩/恢复内核，不属于本步目标。

### 步骤 9：收薄 Electron Main、完成重连与页面回收

**进入条件：** 步骤 8 通过。到此才可以删除 Main 业务宿主的最后依赖。

**必须按这个顺序执行：**

1. 将 Main 生产装配收敛为 UI/平台代理和 Core 客户端；清理旧 scheduler、业务恢复扫描、应用写库连接、主 Pi 实例及 Main 本地执行适配。
2. 删除“Core 失败就恢复 Node 写入/调度”的生产路径；测试替身具名且隔离。旧 `--resident-host` 若保留为兼容入口，只转交新的生命周期管理，不重启旧业务 composition。
3. 让打开/关闭窗口只影响 UI 订阅和页面资源；界面重开先拿权威快照，再按游标接增量事件。游标失效时重同步，不能显示旧缓存为当前真源。
4. 实施隐藏页面/闲置 WebContents 的回收与恢复策略。用户输入、必要登录态和活动平台任务按已定义策略保留；回收记录与进程/内存指标可观察。
5. 复核依赖图和运行期轨迹：Main 不再装配完整 Agent/Work/Cron/Dots/Gateway/Gadget 管理服务；迁移前后的面向用户入口保持可用。

**通过标准：** RC-23、RC-24 通过；所有 UI 关闭和多次重开不改变后台 owner；未读状态、任务进度和结果不丢失/重复；旧 Main 业务路径没有生产入口。

**禁止跨步：** 仅减少 `index.ts` 行数或将旧代码移动到另一个 Node 文件，不算薄 Main 完成。

## 4. 全过程保持的契约

1. **单一业务权威。** 每项业务控制职责只有一个有效 owner；已完成调度交权的域只有 Rust owner 可发出新调度，未交权的域仍由清单登记的原 owner 负责。交接期间不得新旧并行，Main 客户端和 Pi 执行者也不得另建调度权。
2. **应用写入与 Pi 写入分域。** 已迁应用域的写入只归 Rust；未迁域按清单保留原写入路径及切换边界，步骤 4 出口必须关闭全部生产 Node 应用库写入。Pi 原生存储始终由 Pi 持有唯一写入权。数据库“多连接”不等于允许多个未协调的业务写入者。
3. **事务不跨进程悬挂。** 不持有 SQLite 写锁等待模型、网络、用户操作或另一个进程。长操作分阶段，轻查询/取消/续租的进度不依赖长任务终态。
4. **未知不是失败，也不是成功。** 已发出且效果不确定的操作保留身份并核对；不得换 ID 自动重放，不得静默回退到另一实现再执行。过期回执、缺少结果和断连均不能证明未执行。
5. **停止与回收可核对。** pause/cancel/stop 先停止新准入，再处理在途、回执、checkpoint 和权限；取消确认不等于在途效果已撤销。旧代迟到结果只能按身份结算，不能复活旧 owner。
6. **并发按资源组织。** 独立读/计算和不同任务允许并发；同一 SQLite 写提交仍受其写入约束；不靠无限线程、无限队列或盲拆数据库掩盖拥塞。
7. **持久事实优先。** UI、通知与远程页面是投影；事务提交、操作回执、执行存储及事件游标可核对，不能把内存回调当作唯一完成证据。
8. **保留现行业务语义。** 前台插话、后台委派、长期 watch、部分成果、自动归档和未知外部效果处理不得退化；已退役功能不得借迁移复活。

## 6. 最终必须连起来跑的完整故事

单个模块通过后，必须在同一候选版本、同一组受控数据上完成以下顺序。该故事在 Windows、Linux 各执行一次；命令行和 GUI 的证据分别保存。

1. 从实际交付程序启动，登记 Electron、Core supervisor/worker、Pi Host 和业务后端 PID、generation、二进制哈希及真实数据目录。
2. 启动一个会持续产生可核对成果的真实 Pi Work、一个 Cron、一个 Dots 委派场景、一个测试渠道连接、一个静态 Gadget 和一个有业务后端的 Gadget。
3. 在后台执行期间进行前台提问、修改要求和取消另一项任务；确认前台响应和控制通道没有被长操作阻塞。
4. 执行“退出界面”，核对整个界面 Main/Renderer 已退出。非桌面后台工作继续；平台依赖工作按约定唤起代理或等待，不启动旧 Electron 业务 composition。
5. UI 离线期间触发 Cron、发送渠道消息、写 Gadget 数据，核对持久事件和实际效果。
6. 重新打开 UI，以快照+游标恢复；对比任务身份、进度、未读、成果和外发记录，无重复执行/投递。
7. 分别对 Pi Host、Core worker、Core supervisor 注入故障；每次等待已定义的恢复或熔断终态，核对原操作身份、锁、存储和效果计数。
8. 执行一项长资料库维护操作，同时查询历史、续租、发送取消/状态请求；验证独立控制路径、在途计数和冻结的延迟预算。
9. 再执行“停止助理”，确认所有受管业务停止准入并完成规定的结算/清理，自有子孙进程退出，Core 锁和 Pi 租约可安全重新取得，自动拉起策略被停用；随后显式启动，按持久状态恢复。
10. 执行受控版本升级及系统重启，检查同数据目录唯一 owner、不可变二进制交接和常驻设置；重开 UI 继续核对步骤 2 的任务与数据。

外部效果至少包含一个支持幂等/回查的 fixture 和一个不支持回查的 fixture；后者出现 unknown 是正确结果，自动重放产生第二次效果是失败。

## 7. 性能和资源验收

### 7.1 先定测试条件，再比较结果

步骤 1 必须记录机器/系统、构建类型、数据规模、模型与网络是否为 fixture、并发度、预热方式、采样次数、测量工具、后台干扰和当前数值预算。性能用例串行执行，不能和构建或其他压力测试争抢资源。

每个场景保存原始样本和 p50/p95/p99、最大延迟、事件循环延迟、各进程及整组进程的峰值/稳态内存、CPU、队列深度、在途数、错误分类和 unknown 核对结果。样本不足以估计 p99 时标注不可用，不能用少量样本伪造稳定分位数。

已有脚本的明确预算继续作为门禁。新增场景须在迁移实现前冻结具体数值，至少包括 `request_p95_ms_max`、`control_ack_p95_ms_max`、`event_loop_delay_ms_max`、`rss_peak_bytes_max`、`queue_depth_max`、`recovery_deadline_ms`；不适用字段标原因。**这些字段未填完，步骤 1 不通过；不得测完后放宽预算来接受回归。**

### 7.2 必须覆盖的场景

| 场景 | 核心观察 | 通过要求 |
| --- | --- | --- |
| 冷启动、已有 Core 时热启动、重新打开 UI | 各阶段耗时、首个可交互界面、后台 ready 时间 | 满足冻结预算；UI 首屏不等待不必要的网络/历史扫描 |
| 大历史分页与持续流式输出 | 查询延迟、Main/Renderer 卡顿、快照寿命 | 被动读取不触发执行；列表和前台控制满足预算 |
| 大文件导入/删除/备份/恢复叠加轻查询 | 长任务吞吐、轻查询 p95、cancel/status 接收时间 | 轻查询/控制不等待长任务终态；长任务仍前进，无饿死 |
| SQLite 写锁争用、队列过载与取消风暴 | writer 等待、队列/在途数量、主循环延迟 | 界限明确、拒绝可观察、unknown 分类正确；不靠无限排队隐藏过载 |
| 静态 Gadget 数量增长与业务后端启停 | 进程清单、总内存、共享 Host 开销 | 静态 Host 的 Node 增量为 0；按需后端无孤儿；总资源满足预算 |
| UI 反复退出/重连、隐藏页面回收 | 内存、句柄/连接/订阅数、owner 代次 | 20 次循环后资源回到冻结的稳定区间，无单调泄漏；后台执行身份不变 |
| 持续运行与故障恢复 | 队列收敛、event/outbox 积压、恢复时间 | 至少完成一轮 8 小时真实常驻观测；长期计划用可控时钟补测，不能据此声称已经实跑 365 天 |

不得直接承诺“Rust 一定快若干倍”。验收同时检查行为正确、响应预算、结构性进程减少和真实资源数据；单项吞吐提高但前台响应回退，仍判失败。

## 10. 最终完成定义

只有以下项目全部有对应候选版本的证据，才可宣布“后台 Rust 化、Electron 负责界面、Pi 保留独立 Node”完成：

- [ ] 应用域所有权和生产入口已逐项归属，Rust 是应用数据及业务调度权威。
- [ ] Work/Cron/Dots/Gateway/Remote/Gadget 的后台生命周期不依赖 Electron Main 的业务装配。
- [ ] 静态 Gadget 由共享 Rust Host 服务，业务后端按需运行并可回收。
- [ ] Pi 保留当前 Node 实现与原生存储，主执行已进入独立、受管理的 Node Host。
- [ ] 停止整个 Electron 界面进程后，非桌面后台任务继续；平台依赖任务按明确能力状态运行或等待。
- [ ] UI 重开能恢复当前状态和事件；关闭/重开不会重复执行、抢写或丢结果。
- [ ] Core/Pi/业务后端的故障、未知结果、升级、自启与显式停止均有可复现证据。
- [ ] 响应和资源预算通过真实测量，前台并发与长期跟进能力没有退化。
- [ ] Windows/Linux 的原生、GUI、产物和实际发行包验收分别通过。
- [ ] 报告、源码、二进制和实际交付包一致，必需场景无 failed / blocked / not-run。
