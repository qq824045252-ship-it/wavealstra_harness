# Work 团队实现与验收记录

## 本次范围

- 在 Bot 模式选择负责人和成员，填写目标、逐人职责、工作区、验收条件与团队预算。
- 持久化团队计划、执行身份、冻结输入、历史结果和模板。模板只复用成员与分工，不复用授权或自动执行。
- 使用现有 Durable 执行器，不建立第二套模型执行引擎。成员顺序执行，当前负责人单独执行只读汇总。
- 团队在成员与负责人列表中可见；协作和真实执行结果在事项详情显示。成员查询不授予负责人控制权。
- 真实资源门禁限定所选目录和当前 Bot 授权；禁止不透明 shell、外部连接、桌面控制、目录替换和符号链接逃逸。
- 重启、暂停、交接与结果回报沿用持久身份；未知执行或效果不得重发。只有未启动准备可显式重试。
- 修改要求后可显式安排只读复核，保留历史成果但不把历史效果或验收自动当成新版本成功。
- 独立于 Work 的无限 Bot 群聊不在本次范围。负责人汇总仍是待验收成果，用户评审和关闭沿用既有流程。

## 验证依据

1. `test:bot-work-team-service`：事务与幂等、授权与外用户隔离、模板、真实 adapter 分派、冻结输入、资源身份、重试、撤销授权、要求变更、交接和未知效果围栏。
2. `test:bot-work-team-native`：真实新建四个 Bot，经生产队列与 Durable 创建三个根执行；实际读取文件并拒绝越权写入/目录外读取。第一成员结束后暂停、交接到第四个 Bot、关闭并重开数据库与运行时；暂停时不执行，恢复后第二成员和新负责人执行。共三个稳定 Task 身份、七次本地模型调用，重开和重放不新增执行。
3. `test:bot-work-team-access`：参与事项可查询，但成员不能冒充负责人控制，Bot 原授权不变，IPC 仅接受可信主窗口主 frame。
4. `test:bot-team-ui`：18 项真实 React 交互场景，包括新建、模板、迟到回执、原请求重试、导航竞争、改名/交接后的幂等回执及授权撤销后的撤选。此 DOM 测试没有布局或原生焦点，不能替代桌面验收。

## 历史恢复测试护栏

全量检查发现旧 `session-history-recovery` 测试直接把重复 ID 的循环父链交给上游 Pi。干净 b688530 与候选旧测试 bundle 的 SHA256 都是 `830c384a27fa9dec1364dc56de18d76f2c2e1bbc39a9afc710d6c79bb5f94a47`，均可复现内存耗尽；生产恢复入口已有循环预检，并非本次团队改动引起。

保留上游探针，但迁入 128 MB heap、4 秒超时的隔离子进程，验证探针确实到达损坏夹具才允许异常或触及边界。生产恢复、原文件哈希、临时目录清理和 UI 接线断言全部保留。256 MB 父进程、512 MB 护栏下测试通过；未扩宽失败基线。

## 实际桌面验收（开发模式通过）

使用隔离 HOME、独立源码检出、仅监听回环地址的本地确定性模型服务和独立测试文件，未使用真实账户凭据或发送外部消息。Bot、模板、Work、评审和关闭全部通过真实 Electron 窗口操作创建，没有直接写数据库制造执行成功。只读数据库、模型请求日志和文件哈希用于交叉核对屏幕结果。

### 启动与版本边界

仅运行 `pnpm dev`，没有运行产品 build、打包或安装。默认开发配置在 2048 MB heap 下发生 V8 OOM，2560/3072 MB 下被系统以 137 终止。仓库外的临时开发配置外置同版本已安装依赖，保留 Pi 打包，以 1792 MB heap 生成并启动实际开发主进程及 preload；渲染服务同时启动仍曾被系统终止。

随后使用 electron-vite 支持的 `pnpm dev --rendererOnly --config <临时配置>`，复用刚生成的同一份 main/preload，仅启动渲染开发服务与 Electron；1024 MB heap 下窗口和操作稳定。临时配置没有提交仓库，默认开发流程的内存占用问题没有被宣称已修复。

本节真实桌面运行的产品源码是 `742d92d0b15ca98626a2d7660b85cbab9614a82a`。后续预算围栏修复 `1b4773fca81c661a8680bcd11089fe4fafd0a33f` 单独通过服务和原生执行测试，不能把此处截图当成该后续修复或审批集成树的完整桌面验收。

### 从首次建队到完成、重启

1. 在真实窗口中新建 `Team Owner`、`Alpha Reviewer`、`Beta Reviewer` 三个 Bot。选择负责人、两个成员和逐人职责，保存模板 `Read-only source reviewers`。此时数据库没有 Work 或执行，模型调用为零，确认保存模板不会开工。
2. 关闭、重开组队表单并选择模板；填写新目标、隔离工作区、验收条件与预算，创建 `Team desktop acceptance confirmed`。两个成员分别通过生产 native `read` 工具读取 `alpha.txt` 和 `beta.txt`，不是把预写答案直接交给 UI。
3. 两名成员各有独立持久 Task，负责人再建立第三个独立 Task，接收两个已回报成果并汇总。共五次成功的本地 HTTP 模型调用：每名成员一次工具请求、一次工具回执后的回答，负责人一次汇总。两份原文在成员结果和负责人汇总中均准确出现，测试文件哈希未变。
4. 屏幕显示三个成果仍待验收，事项没有自动完成。逐项接受三份交付，再填写当前要求版本的实际验证环境、来源和验证结果，使验收条件从未满足变为满足。
5. 通过结束事项表单填写说明并确认关闭。屏幕和只读存储均确认 `closed` / `succeeded`、三个已接受交付和一个已满足条件。
6. 仅对该隔离 Electron 主进程发 SIGTERM 后重启开发实例，从已完成列表重开事项。三个 binding / Task 身份完全不变，已接受交付、关闭结论和模板保留；本地模型成功调用仍为五次，没有额外派发或结果重放。核验后关闭隔离测试实例。

保留的验收材料包括 `team-setup.jpg`、`team-awaiting-review.jpg`、`team-completed-after-restart.jpg`，以及重启前身份/成果/文件哈希的 JSON 和重启一致性核对记录。它们来自本次隔离测试目录，不含真实账户资料。

### 实际失败路径发现的预算缺口

首次桌面试跑的本地模型夹具只解析最后一条 user 消息，但生产执行器会补充协作上下文，导致两次 HTTP 500。此前试跑没有被改写成成功：失败成果和未知用量保持原状。修正夹具为查找真实冻结的 `teamAssignment` 后，另建上面的成功事项。

失败路径同时暴露生产缺口：generation 用量未知而 dispatch 预留已释放时，团队仍准备下一个成员/汇总执行。补丁 `1b4773f` 将同一 Work 任意未知预算预留纳入准备、派发和重新规划围栏，保留已结束执行的结果回报；暂停和终态显示仍优先。测试经生产预算 API 制造真实未知 generation 状态，验证没有新 Task 或模型提交、不能盲目释放，只有既有预算核对流程提供合法证据并结算后才继续，且不重放原执行。`test:bot-work-team-service` 与 `test:bot-work-team-native` 在该补丁上通过。

默认完整 GUI、ARTIFACT、联网模型、Windows/macOS、Omarchy / Hyprland 真实输入链和发行包验证未运行。本节是云端 Linux 真实 Electron 开发窗口验收，不代替这些门禁，也不证明模型在开放任务上的协作质量。
