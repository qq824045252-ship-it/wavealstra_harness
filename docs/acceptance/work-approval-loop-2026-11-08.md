## 真实桌面结果

1. 从实际 Bot 对话创建无项目目录的事项，后台依次执行 `pwd → write → ls → cat`。写入前，原目录没有目标文件；对话底部和待决定入口显示持久审批，缺失 scope 未明确勾选时不能批准。
2. 批准路径：勾选仅本次范围后批准，真实文件写入并由 `cat` 读回；审批状态为 consumed。拒绝路径：write 被阻止，`ls` 不含文件，`cat` 报不存在，目录中确实没有目标文件，审批状态为 denied。两条路径均回到原 Bot 对话。每个 Work 五次后台模型响应，已提交用量 750 tokens，预留及未知用量均为零。
3. 初次桌面暴露批准与执行结算各清除一次同一 blocker，时间戳重写导致两条相同解除反馈。保留初次失败记录；修复后新批准事项只有一条解除消息。重启后总消息 19、provider 日志 21 行、唯一 binding、文件内容和纳秒 mtime 全部保持不变，没有补发或重复执行。
4. 长对话审批卡在底部可见。主动上滚后后台新增反馈没有抢位置，显示“回到最新消息”；用户点击后才回到新审批位置。
5. 在 `b06b9ed` 上，从原拒绝事项详情点击“仅补跑此项”，再次明确批准原 write。新 Task 和新 Durable store 继承原执行目录；原 binding 未变。新增请求仅 `write → ls → cat → final`，不再执行 pwd，也不重提旧 Task。文件出现在原目录，原缺口记录为 `host_approval_continuation_verified / completed`，计划 settled，原/新 blocker 均清除，详情显示必要缺口为零，反馈仍在原对话。

隔离验收材料保留了待批、拒绝详情、修复后结果、重启、主动上滚与最终补跑截图，以及对应 SQLite、文件和 provider 请求证据。旧失败证据未改写为通过。
