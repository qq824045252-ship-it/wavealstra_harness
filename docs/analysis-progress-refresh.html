为什么进度条不自动刷新？

AI 对话流式更新 vs 上下文用量条刷新节奏脱节 —— 根因分析与修复方案（MyBuddy / Electron + pi SDK）

分析对象：ChatInput 底部 context-usage 进度条 链路：Renderer → IPC → AgentService → pi SDK 目标体验：与 pi 终端（TUI）一致

1问题现象

聊天时文字在流式输出、工具在执行，但底部上下文用量进度条完全不动，直到整轮对话全部结束才“跳”一下。

一句话结论 主进程只在 agent_end（整轮结束）时才发一次 context_usage 补丁；对话本身是高频事件流。两者刷新节奏完全脱节 → 视觉上“对话在走、进度条死寂”。

UI 里真正的“进度条”是 ChatInput.tsx 底部工具栏的 .context-usage-bar：宽度 = used / contextWindow 百分比，数据来自 store 的 contextUsedTokens。

2进度条数据链路：从 pi 到 UI

一条数据在 4 层之间流动，每一层都有“只在终点刷新”的问题。

环节位置刷新时机频率
pi SDK agent.state.messages 仅 message_end 时才把消息推入数组；流式中消息在 streamingMessage，不计入 低频（跳变）
AgentService src/main/agent/AgentService.ts prompt() 结束后、agent_end 事件时各发一次 context_usage 补丁 每轮 1~2 次
store appStore.applyAgentPatch 收到 context_usage 补丁才更新 contextUsedTokens（且仅限 activeTask） 被动
UI ChatInput.tsx 纯展示；无定时轮询 getContextUsage 兜底 不主动

对照：一轮对话中，进度条究竟何时才更新？

assistant_start
agent:event → assistant_start
对话 UI 开始流式渲染（high-frequency 通道）
text_delta × N
agent:event → text_delta（每段文本增量）
进度条：无更新（当前消息尚未落定，token 不计入）
tool_execution
agent:event → tool_start / tool_update
进度条：无更新（工具执行中，context 无变化）
message_end
pi 内部：messages.push() ← 落定
进度条：仍无更新（AgentService 没有在此节点发 context_usage）
agent_end
AgentService → emitContextUsage() ✅
进度条：唯一一次刷新（整轮结束时）

3根因剖析：为什么中间节点拿不到新值？

即使我们在每个事件都去调 getContextUsage()，流式阶段它返回的也是旧值 —— 这是 pi 的数据语义决定的。

3.1 数据源：只有 message_end 才入库

pi 的 getContextUsage() 基于 agent.state.messages 估算 token。而 agent-core 的事件处理中：

// node_modules/@earendil-works/pi-agent-core/dist/agent.js
case "message_start":
  this._state.streamingMessage = event.message;   // 流式中：只进 streamingMessage
  break;
case "message_update":
  this._state.streamingMessage = event.message;   // 增量更新仍在 streamingMessage
  break;
case "message_end":
  this._state.streamingMessage = undefined;
  this._state.messages.push(event.message);      // ← 唯一入库点
  break;

3.2 估算公式：最后一条 usage + 尾部估算

// pi-coding-agent/dist/core/compaction/compaction.js
export function estimateContextTokens(messages) {
  const usageInfo = getLastAssistantUsageInfo(messages);   // 最后一条带 usage 的 assistant 消息
  if (!usageInfo) { ... // 纯估算 }
  const usageTokens = calculateContextTokens(usageInfo.usage);
  let trailingTokens = 0;
  for (let i = usageInfo.index + 1; i < messages.length; i++) {
    trailingTokens += estimateTokens(messages[i]);  // 只数已入库消息
  }
  return { tokens: usageTokens + trailingTokens, ... };
}

结论：流式输出 / 思考 / 工具执行期间，当前正在生成的内容都不在 messages 里，所以反复调用 getContextUsage() 数值基本不变。真正的跳变点只有 message_end / turn_end / agent_end —— 而我们的主进程恰恰在这几个中间节点没有补发补丁。

4终端（pi TUI）为什么“自动刷新”？

对比两条实现路线，差距一目了然。

🖥 pi 终端 TUI（interactive-mode.js）

  • 每个 agent 事件都 footer.invalidate() + ui.requestRender()
  • footer 渲染时重新调用 session.getContextUsage()
  • 另有 working spinner、token 统计（usageTotals 随消息落定累积）
  • 刷新节奏与对话事件完全同步

📦 MyBuddy（当前实现）

  • 只在 agent_end / prompt 结束补发一次 context_usage
  • 中间节点（message_end / turn_end / tool_execution_end）不触发刷新
  • 渲染端无定时轮询兜底
  • 进度条整轮只动一次 → “不兼容”
本质差异 终端是“事件驱动 + 每事件重算重绘”；我们是“终点事件一次性推送”。token 数值同样是跳变的，但终端的刷新节奏和对话同步，因此观感上是自动刷新。

5修复方案（待确认后实施）

对齐终端的“事件驱动”思路，再补一个渲染端兜底，双保险。

1

主进程：关键节点补发 context_usage（对齐 TUI）

在 AgentService.createSession 的 subscribe 回调里，对 message_end / turn_end / tool_execution_end / compaction_end 也调用 emitContextUsage()，把“只发一次”变成“每个节点都发”。

// AgentService.ts（示意）
session.subscribe((event) => {
  // …映射补丁…
  if (
    event.type === "message_end" ||
    event.type === "turn_end" ||
    event.type === "tool_execution_end" ||
    event.type === "compaction_end"
  ) {
    this.emitContextUsage(opts.taskId, session);  // 数值虽跳变，节奏却同步
  }
  if (event.type === "agent_end") {
    this.emitContextUsage(opts.taskId, session);  // 原有终点刷新保留
  }
});
2

渲染端：流式期间定时轮询兜底

sendMessage 后启动 ~1.5s 的 interval 调 window.api.agent.getContextUsage(taskId)，收到 assistant_end 后清除。即使主进程某节点漏发，进度条也会自动追上。

3

（可选）store 增加 contextPercent 字段

直接存 percent，避免前端每次用 used / windowTokens 重复计算；同时便于 ToolCallCard / ExecutionTimeline 复用。

预期效果 对话的每个关键节点（一条回复落定、一个工具执行完、一轮结束）进度条都会跟着刷新，刷新节奏与 AI 对话同步 —— 即终端观感。
