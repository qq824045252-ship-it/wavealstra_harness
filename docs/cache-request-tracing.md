# 请求缓存诊断

增量证据账本已解决已验证的跨轮历史替换机制，但真实长任务中仍观察到轮内偶发低命中。历史用量没有保存最终请求，不能据此决定再修改哪一层。0.1.81 增加请求指纹，作为定位依据；不改变缓存策略、消息、工具、采样参数或重试次数。

## 记录位置与边界

聊天模型请求诊断默认写入 `~/.mybuddy/logs/cache-requests-YYYYMMDD.log`，沿用现有日志的按天、4 MiB 文件轮转与保留机制。`MYBUDDY_CACHE_TRACE=0` 可关闭记录。记录失败不阻断模型调用，也不绕过权限、取消和请求大小门禁。

每个模型调用有独立 request ID：

- `provider`：调用方 `onPayload` 替换/修改完成后的请求对象。
- `http`：实际交给 fetch 的 JSON 字符串；独立记录每次发送及 HTTP 状态。
- `result`：对应模型回复的 response ID 哈希、用量和停止原因。
- 可用的会话边界：用户条目、证据账本、重建、压缩及当前操作的哈希。

请求正文、图片、推理签名、工具参数、完整 URL、凭据和完整请求头均不写入日志。内容、参数、工具 schema、路由相关头使用进程私有随机密钥的 HMAC；密钥不落盘。session ID 和 response ID 使用 SHA-256，供与本地会话/网关记录对应。

每项 input/messages 的指纹及第一个差异的字段名可定位“哪条历史变了”。未缓存输入与缓存读取分别保留，避免错误分母。模型返回的实际模型名另存为哈希。

## 明确不作推断的情况

- 进程重启产生新 epoch；不同 epoch 的内容哈希不能相互比较。
- 最多保留 32 条内存比较链、每次最多 4,096 项、16 MiB JSON。超过限制、无法解析、观察失败会标记覆盖不全并中断比较链。
- 任意请求流和 WebSocket 没有最终 HTTP JSON 覆盖。仅有 `onPayload` 不能声称看到了网络请求体。
- 配置了请求大小门禁时，门禁可能把字符串转换为 Request 流；这种发送明确标记为覆盖缺口，不额外消费请求流。
- 稳定的客户端请求不证明网关转发正文或供应商内部缓存节点稳定。
- 用户换轮、压缩、分支和工具配置变化都可能是合法边界。指纹变化本身不是错误判定。

## 审计

```text
pnpm -s cache:trace
pnpm -s cache:trace -- --session <原生 session UUID 或其 SHA-256>
pnpm -s cache:trace -- --dir <日志目录>
```

结果区分：客户端请求变化、重试时请求变化、前缀稳定但低命中、没有可比前驱、历史日志缺口和 HTTP 覆盖缺口。重试与前一个逻辑请求分开比较，避免第二次发送覆盖掉首次发送时的前缀变化。日志序号用于跨轮转文件恢复顺序。

传入父会话 `--session` 也会返回其子代理的记录，各调用带来源和父会话哈希；传入子代理 ID 则只查看该子会话。`historyUncachedTokens` 是“上一成功请求的原始输入总量 − 本次原始缓存读取量”的非负估计，超过 `max(512, 上一请求输入的 8%)` 时标记稳定前缀下的缓存复用不足（低于 50% 为 `stable-prefix-low-cache`，其余为 `stable-prefix-partial-cache`）。低百分比但旧输入已完整命中的调用标记为 `stable-prefix-new-input`，不再把大块新文件内容误报为历史缓存失效。该估计有分块取整和计量差异，不能直接当作浪费或费用节省。

原始输入和缓存读取必须是非负安全整数，缓存读取不能超过输入总量；缺失或无效时，`rawHitRate` 和 `historyUncachedTokens` 保持 `null`，不归零、不截成 100%，原始值及 SDK 归一化值仍保留供核对。`inputTokenState`、`cacheReadState` 和 `rawUsageState` 分别说明输入、缓存和整组计量的有效性。前驱失败、取消、没有成功终态或没有有效原始输入总量时，不用 SDK 默认零值推算历史大小；稳定前缀标记为 `predecessor-usage-unavailable`，具体原因记录在 `previousUsageState`。前驱的原始输入总量有效且成功时，即使其缓存细分缺失，仍可使用该总量。

`pnpm -s test:cache-trace-audit` 使用纯 Node 夹具检查无效计量、失败或缺失前驱、原始与归一化用量不一致、正常增长/部分复用分类及实际日志 CLI。它不需要模型凭据或桌面，不代表真实任务的缓存命中率得到改善。

子代理 Context Contract 增加按任务路径/符号逐步读取及复用未变化区间的指引。文件变化、截断或证据不足时仍要求重新读取，不截断工具返回、不改写历史，也不降低必要的审查和测试要求。提示指引不等同于已经验证了真实任务的命中率提升。

`stable-prefix-low-cache` 是继续检查网关/上游的证据，不是自动给上游定责。`client-request-changed` 应结合第一个差异和边界事件，确定是否为预期变化。

## 长历史回放

```text
pnpm -s cache:replay -- --session-file <会话 JSONL> --from 80 --count 8
pnpm -s cache:replay -- --session-file <会话 JSONL> --from 80 --count 8 --live
```

默认使用模拟 fetch，禁止实际联网；`--live` 使用已配置的 Magpie 模型，最多 12 次调用，每次有 90 秒超时。Windows 下若包管理器把带引号的文件参数原样传递，可在编译后直接用参数数组调用 `node out/tests/cache-long-session-replay.mjs`。

脚本只读取历史文件，通过 Pi 原生投影和当前供应商序列化器回放。它添加固定诊断提示及占位工具声明；原生历史系统条目若存在仍参与投影。原来的临时证据没有被恢复，因此不等同于原始线上请求的完整复原。使用新会话/cache 标识，回复不写回用户会话，模型即使返回工具调用也不会执行。

## Chat Completions 实测补证（2026-11-09）

Omarchy 隔离目录通过真实 Pi 循环与本机 Magpie 的 `opendesign/deepseek-v4.1-flash` 完成 600 行合成 CSV 的四轮分析，共五次模型调用、一次真实文件读取。没有读取用户对话或执行故障注入。

实测发现 Chat Completions 的原始 usage 已进入 provider hook，但没有写入审计使用的 `provider-usage` 记录，导致五次调用全被误标为 `raw-cache-usage-missing`。现按该协议的 `prompt_tokens` / `prompt_tokens_details.cached_tokens` 记录原值，不从 SDK 归一化计数反推。只有同时存在成功结果的调用才能作为历史前驱，usage chunk 本身不代表成功；缺失、无效和失败仍保持未知。

修后同任务五次原始输入/缓存读取分别为 4044/2048、8887/3968、9068/8832、9239/8960、9454/9216；最后三次约 97%，四次客户端 HTTP 前缀均保持追加。该结果证明此隔离样本已可正确观测，只覆盖这组请求、模型和路由。未将测试模型的零成本元数据解释为实际免费。

另补测 6000 行长输入，同样四轮/五次调用、仅一次读文件：输入/缓存分别为 4045/3712、57089/3968、57308/57088、57460/57216、57641/57344。插入新 CSV 时命中比例约 7%，正确识别为新输入而非历史缓存失效；随后三次约 99.5%，HTTP 前缀保持追加。不是冷缓存对照实验，不能据此估算费用节省。
