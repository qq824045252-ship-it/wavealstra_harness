本文件是完整交付的验收契约，不是测试执行报告。现有测试可以复用，但不能把子代理、Cron 或回执的局部通过等同于整个 Bot / Work 功能通过。实现拆分不减少下述范围；不要求旧数据迁移或旧 Pi 版本兼容。

## 1. 验证环境与证据要求

1. 使用临时数据库、Durable 存储、工作区与用户配置，不访问真实用户凭据或修改真实项目。
2. 模型与外部效果可以使用可控本地 fixture；测试需要记录请求、幂等键、实际效果次数、响应丢失和回执状态。假代理不能替代全部原生 Durable 集成验证。
3. 崩溃场景必须在明确持久化边界故障注入并重新打开存储；仅丢弃内存对象后继续同一调用不构成重启验证。
4. 时区、时钟、timer 与来源事件序列可注入，以覆盖重复、延迟、乱序、休眠与错过触发。不得靠长时间 shell sleep 模拟长期调度。
5. 涉及桌面输入和焦点的场景必须使用真实受支持桌面会话及隔离靶应用；headless fixture 只证明控制规则，不证明真实输入链路。
6. 原生执行、业务控制、界面投影和外部投递证据分别记录。源码存在、编译通过、fixture 通过和实机通过不能互相代替。
7. 执行检查遵守当前仓库 AGENTS.md。设计文档变更本身只做内容和链接核对；运行代码实现之后按改动执行类型检查、相关行为测试与适用集成/实机验收，发布操作遵守单独的授权范围。

建议每次验收记录：源码 SHA、设计版本、场景 ID、环境、输入快照、Work / operation / submission 身份、故障注入点、实际输出、关键数据库记录、效果计数、结论和未覆盖范围。每项必须标注 passed / failed / not-run / blocked；缺少环境只能标 blocked，不能转成 passed。

## 9. 必须串起来的端到端故事

以下是测试情境，不是已执行的真实用户任务：

1. 用户委托“持续跟进这次 Linux 修复，直到我的 Omarchy 实测通过”。建立有限 Work，保存主负责人、验收条件、仓库范围与已有授权。
2. 收到提交 A 的 hook 以及其重复投递。生成一份对应逻辑检查，后台独立执行，前台仍可交流。
3. 用户在检查中补充“只检查 Linux，先别发布”。新要求提交并失效受影响的旧执行与未发出指令；已有在途操作如实结算。
4. 在投递回执保存前注入一次宿主崩溃。重启后找回原执行，没有第二份相同逻辑工作。
5. 旧要求的结果晚到。保存为带版本的证据，不覆盖当前结论。
6. 当前检查完成；至少一个分支模拟“child 正常结束但必要写入被阻止”。保留原生 blocked、writeConflicts 与 isError，负责人根据实际成果决定缺口，保留有效产出，不用 succeeded 计数代替验收或整批重跑。
7. 完成补充工作后，显示“代码与自动检查通过，等待 Omarchy 实测”，提供与当前版本对应的步骤。
8. 用户从手机反馈“第二步失败”，反馈接回原 Work 和实测版本；协作者继续处理。期间交接一次负责人，旧控制决定失效，仍有效成果由新负责人接管。
9. 当前版本实机条件满足后关闭该有限 Work，停用只属于它的订阅；其他 watch Work 保持 active。
10. 通知投递失败后恢复，用户收到/看到已有结果；后台工作不因此重跑。界面能解释整个事项的要求变化、责任交接、当前成果与实际验证范围。

需要组合真实业务服务、真实临时 SQLite、原生 Durable、本地 fixture 模型/效果端点与桌面/移动视图验证。真实 Omarchy 操作另以隔离靶应用提供实机证据，不能把 fixture 的成功声明当成桌面验收。

## 10. 可复用基础与验收完成定义

已有的 [Durable 子代理测试](../scripts/durable-subagent-test.ts)、[写冲突测试](../scripts/subagent-write-conflict-test.ts)、[Cron 调度测试](../scripts/cron-scheduling-test.ts)、[本地工作流集成测试](../scripts/local-workflow-integration-test.ts) 和 [Durable 同步测试](../scripts/durable-sync-test.ts) 可作为基础。这些链接说明现有覆盖点，不声明本次运行通过。

当前 Durable 子代理测试包含“两个 child 正常结束，同时一个同文件写入被拦截”的情境，最新断言已是 `1/2 succeeded`、blocked 和 `isError=true`，并保留 `writeConflicts`。接线必须保留这些改进；准确的执行结果仍不替代 Work 验收，BW-A33 需独立验证业务成果。

BOT-WORK-1.0 交付完成必须同时具备：

- 全部适用场景有可追查结果，失败或 blocked 项明确列为未完成，不能通过删除场景或扩大已知失败基线放行。
