## 1. 三层职责

| 层 | 回答的问题 | 现有承载 |
| --- | --- | --- |
| 交互调度 | 这条消息现在就能答什么；用户插话该并行回答、读进度、改原任务还是停止某一步 | 前台回合、前台工具（`reminder_manage`、`work_query_status`、`work_create`、`work_amend`、`schedule_overview` 等）、`foreground_query_requests` |
| 执行调度 | 剩余工作由谁真正推进 | Work + Durable 执行、团队依赖、Cron、Watch、恢复与续做 |
| 回报调度 | 什么值得主动打扰、什么时候能按需读到同一份事实 | 运行中里程碑、结果卡、原会话反馈、`work_query_status` detail |

分类由本次前台理解完成，不额外增加“分类模型 → 规划模型 → 执行模型 → 每步审核模型”的串联链路。

## 2. 默认 11 类场景与分流

| 类型 | 请求示例 | 前台默认行为 | 后续 |
| --- | --- | --- | --- |
| 直接问答/短文本 | 解释概念、简短改写 | 同一前台回合流式给有用答案 | 不建 Work |
| 短实时查询 | 当前 PR 状态、天气 | 前台少量现有工具；必要时先一句具体承接，随后给真实来源 | 默认不建 Work |
| 状态与安排查询 | 到哪了？明天有哪些安排？ | 读已保存事实与当前进度，一两句给结论/下一步；安排类用 `schedule_overview` 一次读取 | 不让在途后台模型停下来写进度 |
| 轻量应用操作 | 日程改到下午 | 单步工具可完成则前台操作，成功才确认 | “有写入”本身不构成建 Work 的理由 |
| 长查询/多源分析 | 对比方案并生成完整报告 | 能证实的部分先答，未核实内容明确标示 | 余下研究进 Work，分阶段补证据 |
| 多步骤实际执行 | 修复/测试/提交/生成文件 | 真实持久受理后释放前台 | 同一 Work 继续，里程碑与终态回流 |
| 纯提醒 | 十分钟后提醒休息 | 保存后准确报时间、时区与宿主边界 | 到期确定性投递；不调用模型、不建 Work |
| 定时实际执行 | 明早检查 PR 并报告 | 保存执行时间与真实动作 | 到时真正查来源/执行/回报，不降格为提醒 |
| 条件/事件触发 | PR 合并后跑回归 | 明确来源、触发方式与检查方式 | 原生事件优先；无事件能力时明确轮询 |
| 持续目标 | 把打开慢持续优化到达标 | 有可执行步骤立即推进 | 执行 → 验证 → 补缺/下一步；只有需要等待才 Watch/事件 |
| 混合请求 | 先判断，能做就实现，晚上提醒我 | 同一原请求关联即时答案 + Work + 提醒 | 各部分互不阻塞，不重复建单 |

必须保持的语义区别：

- “提醒我检查” ≠ “到时替我检查”；纯提醒不得替换为一次未来模型调用。
- “实现每日提醒功能” ≠ “创建每日提醒”。
- “持续优化” ≠ “每小时重新查看一遍”。

## 3. 前台 → 后台的无损移交

进入执行前，前台必须能把下列内容交给同一个原请求关联的 Work，而不是从零重跑：

- 原始用户要求、最新有效修订、明确引用与附件；
- 已核实的资料、来源、已完成步骤、已登记成果快照；
- 剩余操作、依赖、下一次回报条件、原会话/渠道位置；
- 外部写操作的不确定回执与原操作身份（未知效果不重放）。

前台答完已知部分后可以结束当前模型调用；后台结果由独立回报事件接回**同一个用户事项**，不靠保持前台生成流存活来“代表正在聊天”。没有证据可先答时必须如实说明尚未确认的部分，不能先说“没有风险/已经修好”再等测试决定是否撤回。

## 4. 运行中里程碑（P0 主链）

### 4.1 事实契约

每个可用里程碑至少带这些语义（全部复用既有事实源，字段落点见验收报告）：

| 字段/语义 | 目的 |
| --- | --- |
| workId、binding/execution ID、当前 intentRevision + inputSnapshotId | 旧要求的结果不能覆盖新要求 |
| 来源工具/子项/事件 ID、稳定里程碑 ID | 去重、重启可恢复、避免重发 |
| 已确定发现及其来源证据 | 前台直接读真实结论，不从工具日志猜 |
| 已注册可打开的不可变文件快照 | 先交草稿时知道是哪一版，区分“存在”与“可用” |
| 已覆盖的原目标部分、未覆盖缺口、下一步 | 部分交付后仍能推进剩余部分 |
| 是否必须用户输入、是否替代更早结论、投递状态 | 真正重要时才打扰，更新而不是堆积矛盾消息 |

硬性边界：**原生工具完成 ≠ 目标已完成**。推测、未成功写入、没有验证的文件名、原始工具日志不得自动标为“已完成成果”；只有终态结算才判定目标完成。

### 4.2 端到端回流

1. Durable 仍在执行时，按有界增量读取成功子项、证据与已登记文件快照，不全量重扫长 transcript。
2. 先持久化里程碑并校验归属、当前版本与完成证据；Work 保持运行。
3. 同一份投影同时服务后台主动回报与前台 `work_query_status` 中途查询，不产生第二份状态。
4. 回报层按语义变化、合并窗口、版本与去重键决定：只更新活动、只更新结果卡、或在原事项发一条简短实质回报。
5. 进入聊天的事件通常只有：改变结论的新发现、马上可用的部分成果、关键真实阻塞、最终交付。普通状态/内部重试留在活动详情；相近进展合并，不逐条转发工具日志。
6. 用户随时问“现在先给我已经确认的”，立即读取现有里程碑与真实剩余进度，不创建重复 Work，不重跑已发生的外部副作用。
7. 部分成果先可打开/可用；最终成果保留版本历史与未解决缺口。

## 5. 插话、优先级与真实状态

### 5.1 相对优先级

| 优先级 | 处理对象 | 调度行为 |
| --- | --- | --- |
| 最高 | 已有事项的明确停止、改向、补阻塞信息 | 定位原事项并提交修改，在下一次模型/工具边界生效 |
| 高 | 用户正在问的短问题、已知事实、进度/部分成果查询 | 及时返回，不排在长报告、记忆整理之后 |
| 正常 | 已承诺 Work 的必要执行、验证与可用里程碑 | 围绕依赖与首个可用结果推进 |
| 可延后 | 重复观察、记忆/Skill 维护等后台非紧迫工作 | 不拖慢当前交互，但保留执行机会，避免永久饥饿 |

到点确定性提醒独立于模型队列；有明确时间约束的实际任务可由时间约束抬高优先级。优先不取消其他 Work，也不代表已发生的外部写入可以瞬时撤回。

### 5.2 插话目标解析（宿主可判定）

按以下顺序确定用户要控制的事项，歧义就只问一个必要问题：

1. 用户原文/引用中明确出现的 `work-…` ID；
2. 被引用消息已关联的 Work；
3. 当前 UI 选中的卡片；
4. 用户原文里字面点名的**唯一**未结束事项标题（不少于 4 字，唯一匹配；多个匹配即拒绝）；
5. 只有一个未结束事项时才接受隐式指向。

“这轮只修历史读取”这类没有控制关键词、但语义上改变原要求的消息，走 `work_amend` + 要求版本 + 旧执行失效链；抱怨、催促、质疑不是暂停或取消意图。

### 5.3 承诺与实际状态一致

- 宿主决定不再续做时，主回复正文、下一步与事项状态必须一起改变，不能保留“接下来继续做”。
- 无关的未知外部写入只限制本动作及其依赖步骤，不阻塞独立只读工作；未知效果不重放、不隐瞒。
- 新修订已产出可用成果时，旧修订的失联执行不能让当前版本无限期无法交付，旧风险仍需在结算说明中保留。

## 6. 未来安排：提醒、定时执行、事件与持续目标

| 语义 | 必须做到 | 复用 |
| --- | --- | --- |
| 纯提醒 | 创建/改期/暂停/恢复/稍后；到期直接投递；到期额外模型调用 0、新增 Work 0 | `reminder_manage` → CronService → CronReminderDelivery |
| 定时实际执行 | 到点真实查来源/执行，回报有来源的结果 | Watch/Work 调度的持久订阅 |
| 条件/事件触发 | 有真实事件源就订阅，否则明确轮询与限制；“条件已满足”可先核对当前状态，“下次发生”不能拿历史事件误触发 | WorkWatchIngress 来源/过滤/版本水位/去重 |
| 持续目标 | 有可执行步骤就推进，验证后补缺/下一步；只有需要等待时才挂时间或事件 | Once + 续做 + Watch |

### 6.1 无变化快路径

宿主已证明来源未变化（`comparisonState=unchanged`）且本轮可静默时，只要目标/偏好版本未变、没有新缺项、没有到期或停止条件，本轮不再调用结果整理模型，直接持久化“宿主证明无变化”的静默记录。来源读取失败、不可比或确有变化必须仍走结果回合；静默不等于没有模型开销，验收以额外审查调用为 0 为准。

### 6.2 统一“我的安排”

用户问“明天有哪些提醒和跟进”时，一次读取现有提醒、定时执行、事件关注与持续目标，回答：事项/提醒、具体时间或触发条件、真实将做什么、当前状态、结果回到哪里。底层仍各归 Cron/Work/Watch，修改继续路由到原对象；宿主离线或休眠必须显式呈现，不能与“已经安排”混为一谈。

## 8. 验收顺序与状态口径

1. 冻结默认场景与“立即答案/余下工作/下次回报”契约，接好原请求 → 原 Work 关联；
2. 运行中里程碑与原前台回流；同批修 B-2 可靠性；
3. 插话、控制与当前问答优先路径；
4. 统一安排查询、真实事件触发与持续目标闭环；
5. 跑 3 个完整故事与相关回归，记录真实耗时/模型调用并同步文档。

结果口径必须区分：任务最终完成、可验证部分交付、明确阻塞、未知效果、状态不一致。不要把 native `completed` 一律当作用户目标完成，也不要把 500 ms 收条当首个实质回答。

## 9. 关联缺口（不得在本 Issue 完成时宣称已解决）

- 长会话历史召回（300/301 边界）与完整 Git SHA/普通技术词误过滤；
- 桌面 → 网关 → 桌面同一 Bot 的稳定偏好与事项指向、网关自动记忆 scope 差异；
- 无 project 的个人 Work/聊天经验能否成为跨 Work Skill，以及修订后的效果证据；
- QQ/Discord/钉钉主动通知与文件交付、离线电脑之外的常驻执行；
- 真实桌面/模型/任务链的整链路验收（本轮以服务级与投影级夹具为主，明确区分模拟与真实）。
