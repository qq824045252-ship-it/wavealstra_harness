# Bot 持续委托接单契约

## 同一轮模型调用，两个不同事实

`work_create` 必须显式提交：

- `requestedOutcome: one_time | ongoing`：模型对用户目标及上下文的理解，不是用户原话，也不覆盖宿主独立保存的原始消息。
- `mode: once | watch`：实际执行计划。不会因省略字段而默认变成一次性任务。

宿主只验证结构一致性，不使用中文关键词、不要求用户逐字引用频率，也不增加第二个接单模型调用或用户审批。

- `ongoing` 不能落 `once`，也不能只留一次 `nextWakeAt`。目前前台持续计划须有有效周期 Cron。
- `one_time` 可以使用 `watch` + `nextWakeAt` 安排一次未来跟进，但不能附加无限周期 Cron。
- 创建 `watch` 必须保存有效时间表，成功回执中的 `nextWakeAt` 来自实际订阅。未安排、已到点和非活动状态不能冒充 `scheduled`。
- 时间安排须标记 `scheduleBasis: user_specified | recommended`。推荐安排需有 `scheduleRationale`，保存在规则中，回执与详情页说明这是建议且可更改。用户没有给频率时可结合任务提出合理低频安排并透明说明，不机械追加确认。

原有任务不会因为升级而改模式、重开、增加订阅或更改用户数据。

## 能力边界

宿主能阻止“模型已明确理解为持续，却创建一次性计划”的结构矛盾；不能以通用、确定的规则判断所有自然语言。如果模型将原意和计划一起误判为一次性，结构校验无法发现。此问题只能通过语义能力、提示和真实反例验证持续改进，不宣称已获得可靠的自然语言意图证明。

原文中的“实现持续追踪功能”“总结过去每日记录”不必代表让 Bot 持续监控。否定、英语和依赖前文的简短选项同样由本轮模型理解，宿主不以词语匹配替代语义。

## 验证

- `pnpm -s test:bot-watch-intake`：真实前台工具/SQLite/WorkService，验证缺字段、结构矛盾和不合法时间表均不产生 Work 或派发；验证推荐依据持久化、实际下次检查和一次性未来跟进。
- `pnpm -s test:bot-watch-intent:live`：隔离 HOME 的 `pnpm dev`、真实 Electron UI 和真实模型，覆盖上下文选择持续、英语时间表、历史周期数据、描述监控功能、明确否定及一次未来检查。保存模型建单参数与持久任务事实，不修改生产任务，不进行崩溃注入。

真实验收发现的澄清、误分类或失败必须留在报告中，不能用测试预填正确参数代替自然语言路径。

### Omarchy 实测（2026-11-10）

在隔离 HOME 通过真实 Electron `pnpm dev` 和 `opendesign/deepseek-v4.1-flash` 完成六条用例：

- 前文明确只读文件目标后，用户仅选择“2，持续追踪”：无需追加频率确认，创建周期 watch；回复说明每 30 分钟是建议、首次时间、时区及可更改。
- 英文每周一上海 09:00：实际持久周期与未来时间正确。
- 历史每日数据总结、说明如何实现监控功能、明确不持续：三条都创建 once，后台实际完成。
- 只做一次未来检查：watch 下的一次性 nextWakeAt，没有周期；取消后不再检查。

最初测试夹具只写“某个测试事项”而没有目标，模型没有建单并询问目标。该失败报告保留；补上具体隔离测试文件后六条通过。未把询问必要目标当作产品错误，也未预填工具参数。

报告保存实际模型建单参数、前台原文、持久 Work/订阅和正常取消结果。所有测试使用合成事项，不重开或迁移历史生产事项；本轮不包含崩溃注入或打包验收。
