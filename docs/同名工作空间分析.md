# 同名工作空间问题分析报告

> 调研日期：2026-08-06
> 调研范围：仅代码检索与数据库取证，未做任何修改
> 结论：**当前设计没有「空间名称唯一性」保障，同名空间是必然可能出现的，且本机数据库已存在实例。**

---

## 1. 结论摘要

| 层面 | 是否存在名称唯一性约束 | 证据 |
|---|---|---|
| SQLite 表结构 | ❌ 无（`name` 无 UNIQUE，仅 `id` 主键） | `PRAGMA index_list(spaces)` 仅有主键索引 |
| 前端去重逻辑 | ❌ 仅按 `path` 去重，不按 `name` | `addSpaceFromPath()` 只比较路径 |
| 前端自动命名 | ❌ `工作空间 N` 按列表长度顺延，无查重 | `addSpace()` 直接 `spaces.length + 1` |
| 主进程 IPC | ❌ 直接写库，无校验 | `ipcMain.handle(DbIpc.upsertSpace)` 原样透传 |

**本机实测**：`~/.mybuddy/app.db` 的 `spaces` 表中已存在两个名称完全相同的「周报系统」空间（见 §3），用户在「新建任务 → 选择工作空间」时就会看到两条一模一样的记录。

## 2. 空间创建的三条路径

### 路径 A：新建工作空间按钮（自动命名）

- 入口：`WorkspacePicker.tsx` 底部「新建工作空间」
- 实现：`src/renderer/src/store/appStore.ts` → `addSpace()`

```ts
addSpace: () => {
  const n = get().spaces.length + 1;
  const space: Space = { id: uid(), name: `工作空间 ${n}` };  // 无查重
  ...
  void window.api?.db?.upsertSpace({ id: space.id, name: space.name, path: space.path });
},
```

- 名字由 `spaces.length + 1` 顺延生成，**不检查是否已存在同名**。只要列表长度发生过回退（未来若加入删除空间功能、或 DB 被清理），`工作空间 N` 就会撞名。

### 路径 B：打开本地文件夹（按文件夹名命名）

- 入口：输入框下拉「打开本地文件夹」（`appStore.openLocalFolder`）
- 实现：`addSpaceFromPath(folderPath, name)`

```ts
addSpaceFromPath: (folderPath, name) => {
  const normalized = folderPath.replace(/[\\/]+$/, "");
  const existing = get().spaces.find(
    (s) => s.path && s.path.replace(/[\\/]+$/, "").toLowerCase() === normalized.toLowerCase(),
  );
  if (existing) { ...return existing.id; }   // ← 只按 PATH 去重
  const space: Space = {
    id: uid(),
    name: name || normalized.split(/[\\/]/).pop() || normalized,
    path: normalized,
  };
  ...
},
```

- 去重条件 `s.path && ...`：**只有当旧空间有 `path` 且路径相同（忽略大小写）时才复用**。
- 两个不同路径、但文件夹名相同的目录（如 `C:\proj\周报系统` 与 `D:\proj\周报系统`），会创建两个同名空间。
- 更关键的漏洞：**旧空间 `path` 为 NULL 时去重直接失效**（见 §3 实测案例）。

### 路径 C：任务写入时主进程自动占位（隐性创建）

- 实现：`src/main/db/AppDatabase.ts` → `upsertTask()`

```ts
if (spaceId) {
  const exists = this.db.prepare("SELECT 1 FROM spaces WHERE id = ?").get(spaceId);
  if (!exists) {
    this.upsertSpace({
      id: spaceId,
      name: task.cwd ? task.cwd.split(/[/\\]/).pop() || spaceId : spaceId,  // 同样无查重
      path: task.cwd,
    });
  }
}
```

- 当任务引用的 `space_id` 在 `spaces` 表不存在时，会**静默补建一个空间**，名字取 `cwd` 的 basename 或 spaceId 本身，同样不做名称查重。这是第三条可能产生同名空间的隐性路径。

## 4. 根因汇总

1. **设计层面**：空间的身份标识是 `id`（UUID 风格），名称被当作纯展示字段，全链路（前端 store → IPC → 主进程 → SQLite）**没有任何一层校验名称唯一性**。
2. **去重逻辑只认 path 不认 name**：`addSpaceFromPath` 的复用条件是「path 存在且相等」，两个漏洞叠加——(a) 不同路径同名目录会建两个同名空间；(b) 旧数据 path 为 NULL 时去重完全失效（本次实际触发点）。
3. **DB 无唯一约束兜底**：`spaces.name` 没有 `UNIQUE` 索引，即使前端漏判，数据库也不会拒绝。
4. **遗留种子数据无 path**：早期 `mockSpaces`（`sp-*`）入库时未带 path，成为后续去重的盲区。

---

## 5. 影响与风险

- **用户困惑**：「新建任务 → 选择工作空间」出现两条相同名称，无法从 UI 区分，可能选错空间导致任务绑定到错误的 cwd/记忆上下文。
- **任务绑定歧义**：`bindTaskSpace` 按 id 绑定，同名不影响内部逻辑，但用户侧无法预判哪个 id 对应哪个目录。
- **记忆串扰风险**：`memories` 按 `space_id` 隔离，两个同名空间若被用户混淆选择，自动记忆 digest 可能落到用户意想不到的空间。
- **无自我修复机制**：没有去重/合并工具，重复数据会一直累积。

## 6. 修复建议（2026-08-06 已全部实施，见 §8）

| 优先级 | 建议 | 状态 |
|---|---|---|
| P0 | `addSpaceFromPath` 去重改为「path 相同 **或** name 相同」时复用/合并；对 path 为 NULL 的同名旧空间优先复用 | ✅ §8.1 |
| P0 | 数据库为 `spaces.name` 增加唯一性保障：`CREATE UNIQUE INDEX idx_spaces_name ON spaces(name)`（需先清理现有重复数据） | ✅ §8.2 / §8.4 |
| P1 | `addSpace()` 自动命名时对现有 name 集合查重，撞名则递增直至不冲突 | ✅ §8.1 |
| P1 | `upsertTask` 占位建空间前，先查 `spaces` 是否有同 path / 同名空间，有则复用其 id | ✅ §8.6 |
| P1 | 提供一次性清理脚本：合并/重命名现有同名空间（本机需处理「周报系统」两条） | ✅ §8.4（实库已执行） |
| P2 | 主进程 `upsertSpace` IPC 增加 name 查重与返回冲突提示；UI 允许重命名空间以消歧 | ✅ §8.3 / §8.5 |

## 8. 修复记录（2026-08-06 已实施）

### 8.1 方向 1：入口去重（store 层）

- `appStore.addSpace`：自动命名改为经 `nextAvailableSpaceName()` 查重，撞名自动递增后缀；写入失败回滚乐观状态
- `appStore.addSpaceFromPath` 三态分支：
  1. **路径相同**（忽略大小写/尾部斜杠）→ 复用现有空间
  2. **同名且旧空间无路径**（历史遗留种子）→ 复用旧空间并回填真实路径（本次「周报系统」问题的直接解法）
  3. **同名但路径不同** → 新建空间并自动加后缀消歧（如 `docs` → `docs 2`），保证不重名
- 新增 `appStore.renameSpace(id, name)`：前端先查重（忽略大小写、排除自身）再调 IPC，失败返回 false

### 8.2 方向 2：数据库唯一约束（DB 层）

- `AppDatabase.migrate()` 新增：`CREATE UNIQUE INDEX IF NOT EXISTS idx_spaces_name ON spaces(name COLLATE NOCASE)`（幂等；若历史库仍残留同名数据则仅告警不阻断启动）
- `upsertSpace` 改为返回生效行 `SpaceDto`；任何同名写入抛 SQLITE_CONSTRAINT
- 新增 `renameSpace(id, name)`、`findSpaceByName`、`findSpaceByPath`

### 8.3 方向 3：IPC 层校验

- `db:upsertSpace` / 新增 `db:renameSpace` 通道：捕获唯一约束异常，返回 `{ ok, space|error }` 结构化结果，不再静默 void
- preload / index.d.ts / agent-ipc.ts 契约同步

### 8.4 方向 4：存量数据治理（已对实库执行）

- 新增 `scripts/dedupe-spaces.ts`（dry-run 默认，`--apply` 执行）：按名称分组 → 保留带 path/最新的 → 迁移 tasks/memories 引用 → 删除冗余 → 建唯一索引
- **实库执行结果**：`~/.mybuddy/app.db` 中「周报系统」×2 已合并为 1 条（保留有真实路径的 `local-1785974113304-1`，`sp-weekly` 无任务/记忆直接移除）；空间数 10 → 9，同名组 0；`idx_spaces_name` 唯一索引已生效
- 操作前已备份到 `~/.mybuddy/backup-<时间戳>/`（含 WAL）

### 8.5 方向 5：UI 消歧

- `WorkspacePicker`：条目显示 path 小字 + title 悬浮提示
- `Sidebar`：空间右键菜单新增「重命名」（内联输入 + 确定/取消 + 冲突/空名错误提示）；空间行 title 显示 path；「打开文件夹」现在直接打开该空间目录

### 8.6 方向 6：堵住隐性创建路径

- `AppDatabase.upsertTask` 占位逻辑重构为 `resolveTaskSpaceId`：
  1. 任务 cwd 命中已有空间 path → 复用其 id
  2. basename 命中「无 path 的同名空间」→ 复用并回填
  3. basename 撞名但路径不同 → 不复用（避免绑错），占位空间名自动加后缀
- 该路径创建的空间同样受唯一索引约束
