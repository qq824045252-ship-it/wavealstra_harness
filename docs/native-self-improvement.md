# MyBuddy 原生会话自我改进规划

目标是让 MyBuddy 在下一次同类任务中更可靠地交付，减少用户补救与无效操作。验收时让改动前后的代理面对相同输入、工具和完成条件，对照最终结果、人工介入和实际调用。复盘记录用来定位决策和解释差异。仅发现问题或发布规则的条目保持待验证。

## 首版交付与验收（2026-11-21）

在「自动化 → 每周复盘」运行复盘。首页查看改进发现，「发布版本」查看回放和运行回执，「子代理交接」查看派发及回答，「历史周报」按周核对验收和人工纠正。展开一项改进可以查看原始来源，也可以停用它。设置中的「自我改进」打开同一份报告。

周任务读取原生提交和工具回执，筛选五类问题，按出现频率、已观测补救耗时、作用域和证据强度排序。每周最多自动采用五项改进。有明确的检查方法及正反例时才发布。证据不足的候选保留四问和原始条目。配置允许时，复盘可以调用模型核对当时可见的技能、策略、工具结果和等待；缺少原生关联的业务结项保留未知。

五类资产共同生效的首个场景是 Markdown 交付。如果用户已经要求章节或附件，代理写过文件又声称完成，随后用户点名指出遗漏，复盘会读取当时登记的产物快照。独立检查器须复现该遗漏，验证后的改进才可生效。

| 资产 | 发布后实际发生的事 |
| --- | --- |
| Hook | 在所属原生代理结束前执行固定版本的检查脚本。仍有缺项时把具体内容送回本轮，允许代理继续补齐。 |
| 脚本／工具 | 宿主检查器读取真实文档和附件，将结构和文件指纹同本轮登记核对。 |
| 技能 | 在角色和技能策略允许时读取版本化的 `SKILL.md`，将方法交给负责工作的代理。 |
| 约定 | 本轮命中明确交付契约时应用作用域内的约定，用户明确修改或取消要求时重新判断。 |
| 记忆 | 按原生来源写入“用户曾指出已明确的交付要求被遗漏”这一事实。召回、来源撤销和作用域核对沿用记忆服务。 |

每包暂存五项资产，记录独立回放结果，按基础版本一次切换。确定性退化会回退或停用；再次发布时还须通过引发撤回的实际输入。周报沿原任务回填，可查看每类资产的使用次数和所在任务的验收结果。共同使用的资产共享交付结果，单项贡献需要单独对照。

### 原文十二个验收场景

`pnpm -s test:improvement-release` 经过真实的 Durable、SQLite、QuickJS、文件系统和子代理，使用可重复的模型应答和模拟周界。

| 序号 | 场景 | 核查的结果 |
| --- | --- | --- |
| 1 | 长历史及已结束子代理 | 从界面窗口之外取回纠正、子工具失败和父返回，分支副本不重复计数。 |
| 2 | 正常需求变化 | 用户新增要求后，原任务保持正常，未产生纠错资产。 |
| 3 | 重复问题 | 两次独立纠正合并为一项；同周重跑保持相同版本。 |
| 4 | 原问题回放 | 原始缺项可复现；后续实际任务据具体反馈补写章节和附件，独立检查通过。 |
| 5 | 同类变体与反例 | 换文件名、章节及附件仍生效；无关问题和其他任务范围无触发。 |
| 6 | 主会话与子代理 | 两者有独立的实际使用及写入记录。父会话代写的文件不能通过子代理本轮验收。 |
| 7 | 已有会话继续 | 同一原生会话下一轮取得新版本，原会话编号保持一致。 |
| 8 | 发布中断 | 暂存后强制终止进程，重开后读取完整旧包。 |
| 9 | 执行中断恢复 | 修复写入落盘后强制终止进程，恢复原提交；两笔修复各执行一次。 |
| 10 | 新版退化 | 特定变体触发真实运行错误后回退，主会话与新子代理恢复使用上一可用版。 |
| 11 | 并发修改同一资产 | 同一基础版本只接受一次发布；合并后重新验证，两个修改均保留。 |
| 12 | 下周回填 | 下周服务运行按版本和资产记录有效、无效、待验证、退化；后到的纠正可更正原任务，无使用机会的周保持待验证。 |

周报写入配置目录下的 `improvement/<UTC 周一>/`。该周的 `current.json` 指向完整快照，其中有 `metrics.jsonl`、`ledger/changes.md`、`replays/summary.json` 和 `retro.md`。文件不包含会话全文。真实用户纠正频率、交付质量或耗时是否改善，要看发布后可比任务的实际样本。

## 改进数据从哪里来

| 数据基座 | 原始事实和关联键 | 当前怎样参与改进 |
| --- | --- | --- |
| 主会话和原始提交 | Durable 的 conversation、submission、entry 与生成任务。原始输入审计记录用户消息、目标续跑和 Bot 请求身份 | 重建当轮要求、回答和后续纠正。导入副本、继承内容、自动续跑不会冒充人工纠正 |
| 原生子代理的任务交接 | 父工具任务和调用编号、子代理身份、角色快照、模型、交接要求、子会话、每次派发的提交编号。新派发还保存当时的父轮提交编号 | 已结束子会话也进入索引。重试保留独立提交。普通、并行、Pstack 嵌套派发按各自原生身份回查 |
| 人工介入和插话 | 子会话的指令文档与原生提交记录请求、状态、放入会话的条目、回答条目和终止原因。主会话的交互表保存提问、选择、回答、取消或过期 | 新插话记录用户或父代理来源。排队、放入会话、已回答分别计数。未处理或未回答的异常形成待归因线索。明确的用户纠正才进入人工纠错判断 |
| 工具执行与恢复 | Durable 工具任务、模型调用编号、结果条目、嵌套调用的所有者、工具诊断 | 子代理逐调用读取，涵盖一条模型消息中的多个工具和已建立的嵌套任务。相同读取失败、恢复成功、遗漏明确要求的回读有专门检测 |
| 最终结果、停止和验收 | 原生输入回执、Work 执行绑定和已登记成果、Dots 正式 Goal 的结项依据、Pstack 检查命令和指纹 | 周复盘用原生会话和本次输入找到对应的 Work 与意图版本。只有执行关单的那次操作能取得该次结项及其依据。普通任务、子代理和没有业务回执的执行各保留其实际结果。 |
| 实际生效的环境资产 | 加载清单、技能调用证据、学习候选与反馈、子代理角色快照、Hook 的版本及执行回执 | 周复盘能按子会话核对角色指纹和实际执行的 Hook 版本。主任务的技能清单与已使用技能由现有学习服务记录。历史子会话缺少逐技能版本时保留未知 |
| 耗时、用量和等待 | 请求诊断、工具诊断、交互的执行编号、创建与结束时间、提供方上报的 token 分量 | 可在交接详情及其归因中核对该子代理的请求数量、新输入、输出、缓存读取和关联等待。只有可定位到同一执行的等待才计入。缺少分量显示未知 |
| 后续任务和改进效果 | 台账保存原生来源、资产指纹、回放、切换历史、各执行者使用及提交结算 | 按原任务的适用周回填五类资产的使用与共同交付结果，跨周收到纠正后可以修订，缺少适用样本继续观察 |

**在产品中核对一次交接。** 打开「设置 → 自我改进 → 原生子代理交接」，展开角色并点「查看交接与结果」。可以沿任务、父会话、派发工具、子会话、插话和回答逐步核查。工具和结果从现存 Durable 数据库只读获取。周复盘保存交接摘要与来源编号。已经扫过消息的旧检查点也会补建子代理索引。

**历史证据边界。** 子代理只有收到原生身份后才计入子会话总数。派发前被拒的项目保留在父工具侧。历史插话没有记录发起方时显示来源未知。旧取消回执只有 aborted 时保留取消状态。有回答和父会话收到返回，各自有独立证据。全局技能版本与人工验收反馈尚无覆盖全部子会话的记录。

只读核对某个本地配置目录可运行 `pnpm -s audit:native-improvement-sources`，也可把配置目录作为首个参数。该命令使用产品的历史读取接口，只输出汇总数量。统计范围是当前配置的全部可读绑定。原生回执以线程内唯一编号去重，模型请求诊断按实际请求计数。

## 从哪里学习

| 观察 | 如何判断 | 下一次改变什么 |
| --- | --- | --- |
| 用户纠正范围 | 将纠正关联到前一个请求及回答。单纯增加要求、取消、只要概要均不算失败 | 遇到明确的范围调整时，对照已有目标、交付物及验收 |
| 相同失败或自行恢复 | 只比较同轮同参数、同错误的连续只读调用。改变输入后成功可定位恢复点 | 提示核对能区分原因的新证据，保留用户明确要求的重试 |
| 错误路径被自行修正 | 主会话原路径返回文件不存在，随后成功读到另一个相对路径下的同名文件 | 下次用户按文件名查找时，在第一次工具调用之前核实已学到的位置。用户明确指定路径时按原路径执行。出现冲突或位置失效即停用 |
| 提前交接或未验证交付 | 区分询问必要信息、真实阻塞和已经明确要求的回读 | 针对明确要求回读的文件，在结束前检查同轮、同文件、写入之后的成功回读 |
| 重复成功操作 | 连续重复相同只读调用、结果也相同，记录可能多余的步骤 | 进入工具或技能改进候选；轮询和需要独立复核的操作须单独判断 |

## 目标执行顺序

1. 先回填以前的版本。将实际运行回执、所属原生会话和后续行为关联。无机会、有触发、已补做、仍复发和退化分开显示。
2. 用只读快照分页扫描已绑定的 Durable 主会话和原生子代理。保留任务、会话、条目和执行者身份。过滤导入及继承副本、自动续跑和咨询辅助会话。检查点与观察结果一起保存；未完成轮次可跨周继续。
3. 聚合同一作用域的证据。单纯改变要求、一次任意异常或任务耗时长，都不足以发布规则。保留自动恢复和重复成功两类正向线索。
4. 为候选保存四项判断：看到了什么，当时缺什么，应该改哪个环节，以及怎样证明改善。归因不足时保留引用和疑点。
5. 选择最小改动。上下文遗漏用范围约定，机械执行问题用工具或流程技能，缺少交付证据用完成检查，稳定偏好交给有来源的记忆，产品缺陷进入源码修复。不同项目的样本不能互相授权。
6. 按证据强度和重复次数排序。每个自然周最多自动发布五项，使用仓库维护的、可回退的模板。涉及未知业务语义、脚本、工具定义或产品代码的候选留给有上下文的维护者。已有人工修订或停用的资产保留其选择。
7. 发布前在原决策输入上回放，再跑同类变体和负对照。记录指纹、版本和验证结果。已有 Hook 执行器负责将约定和检查带入新旧原生主会话及子代理。观察到执行错误时停用对应自动版本。
8. 设置页展示周期、问题、原始来源、改动、真实命中与验证情况；支持立即复盘、停用和检查运行回执。下周继续回填。中断后沿检查点补扫，重复触发合并。

## 交付与验收

- **证据和归因**：持久化原生输入、工具、回答之间的必要引用及指纹。复盘不能唤醒历史任务。重复扫描、分支复制和跨周续跑均只计一次。
- **实际生效**：在独立的原生会话中制造旧问题，运行复盘，在后续任务上观察请求变化或完成前补做，并检查实际文件。普通需求变化、主动取消、明确要求等待或省略验证的任务都应正常结束。
- **运维**：周期检查随桌面调度启停。离线期间新增的记录按历史游标补入，失败的来源单列并重试。人工修订、停用和运行故障可追溯。
- **长期衡量**：分别报告可适用样本、实际触发、补做成功、再次纠正和不确定结果。离线回放及测试模型用于证明机制。减少人工介入、耗时或费用需要后续同类真实任务作对照。

## 已接入的产品行为

入口为 **自动化 → 每周自我改进**，也可以从 **设置 → 自我改进** 进入。应用启动后和运行期间每小时检查 UTC 自然周。桌面关闭期间错过的周期会补扫，手动复盘可以立即检查新增条目。报告默认显示最近十二期，每期的落盘快照保留。

自动应用包括五类资产的交付检查包、三类原生 Hook 及任务内的文件位置经验，共享每周五项名额。只有原始输入和当前任务共同证明项目或工作空间绑定时，才在相应范围复用。文件位置经验始终绑定任务及工作目录。

开启记忆且来源会话有可用模型时，每周可以分析最多五个待归因片段。模型读取带编号的原始摘录，包括可定位的派发、插话、父返回、子回答、工具失败和当轮可见能力。归因须引用一至三个来源编号。受管交付资产可以验证后自动发布；需要修改产品代码或缺少独立验收方法的建议保留在发现详情。

文件回读检查首批支持一句明确的单文件写后回读要求、原生 write/edit 和 read，以及带有宿主调用记录的 Code Mode。绝对路径和相对路径按任务中提供的相同拼写关联。真实阻塞、显式跳过和证据截断时允许报告实际情况。一次成功读取只证明工具读到了文件，内容与业务目标是否一致要由对应验收判断。

### 验证入口

- `pnpm -s test:improvement-release` 验证五类资产及上表十二个场景。
- `pnpm -s test:native-improvement` 验证历史扫描、原生 Hook、文件位置经验和周期额度。
- `pnpm -s test:native-improvement-dev` 打开隔离的开发版 Electron，操作复盘、展开来源和停用按钮，再从原生执行记录核对触发。
- `pnpm -s test:native-hooks` 覆盖通用 Hook 的并发发布、执行拦截、子代理、Code Mode 和崩溃后固定版本。
