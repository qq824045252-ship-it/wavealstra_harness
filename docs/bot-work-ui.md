# BOT-WORK UI：普通模式与 Bot 模式双页面（2026-11-06 已确认入口）

> 本文件保留最初的页面边界与验收计划。以下「2026-11-08 实现更新」描述当前界面；后续原始方案与其冲突时，以实现更新为准。它不改变 F01～F14，也不覆盖 [BW-A01～BW-A46 验收规范](bot-work-acceptance.md)。UI 验证不等于整个 Bot 服务、跨端、真实模型或发行包验收完成。

## 2026-11-08 实现更新

### 日常使用路径

- 普通模式与 Bot 模式在侧栏顶部可直接切换，原账户菜单入口保留。Bot 侧栏仅选择身份，避免与主区重复列出待决事项。
- 主区始终保留「对话 / 进行中 / 待你决定 / 已结束」四个入口。对话不再在长历史之后堆叠事项列表；事项视图支持搜索，消息中的关联事项可直接定位详情，包括尚未载入的已结束事项。
- 聊天复用普通模式的 Markdown 渲染器、气泡、图标和主题色。Bot 不借用后台选中的普通 Task 来解析文件名或路径；文件引用需要从关联事项查看。
- 输入框支持 Enter 发送、Shift+Enter 换行，并保护中文输入法确认键。阅读旧消息时不会被轮询拉回底部，可用「回到最新消息」返回。空对话提供三个可编辑示例，只填入草稿，不自动发送。
- 详情顺序为目标、真实验收进度、下一步、成果与证据、评审。负责人代次、版本、交接、关注、预算和诊断保留在高级区域；未知投递、预算待核对、恢复确认等风险不能因折叠被隐藏。
- 未选择事项时不占用空详情栏。1180px 以下自动收起左栏并采用原生导航/详情抽屉，不改写用户原侧栏偏好。抽屉有键盘焦点约束与 Esc 关闭，跨宽度切换不重建详情表单。
- 已完成、已取消、未达成结束分别呈现；已结束的历史提案不再计作待决事项。进度只来自验收条件，不估算完成百分比。旧记录缺少结束结论时仅显示「已结束」。
- 业务控制仍走现有 Work API，版本保护、幂等操作、结束依据与二次确认保持。归档当前对话需要确认，不删除事项。

## 2026-11-08 独立 Bot 创建补全

### 从首次使用开始

1. 进入「Bot 模式」，点击页面右上角「新建 Bot」，或侧栏「我的 Bot」旁的同名入口。没有身份时，空态也有创建入口。
2. 填写名称（必填，去除首尾空格后 1–80 字）和主要职责（选填，最多 2000 字）。同用户重名按 Unicode NFKC、大小写及首尾空格规范化后拒绝。
3. 确认后创建持久身份及独立专家初始快照，默认选择新 Bot。名称和职责可在「Bot 设置与对话管理」查看；这里不承诺尚未实现的重命名、删除或编辑职责功能。
4. 新 Bot 从空对话开始。创建本身不发送消息、不创建 Task/Work、不连接外部服务。普通聊天走 Bot 对话，明确委托才走现有 Work 受理流程。
5. 在「我的 Bot」切换，分别恢复对话、草稿和该 Bot 的事项。原 MyBuddy 不被替换。

### 安全与恢复边界

- 创建 IPC 仅接受当前宿主拥有的主窗口、顶层 frame 和可信应用文档；用户身份由主进程固定，管理权在持久宿主租约内核验。渲染层不能指定身份、权限、工具或记忆命名空间。
- 名称、职责和请求 UUID 使用严格 schema。新身份采用最小授权、空外部能力列表与独立私人记忆命名空间；创建不扩大工具权限，不修改数据库 schema 或丢弃历史。
- Bot 与专家版本原子写入；同请求同参数幂等回放，不同参数冲突。提交前保存待核对请求，丢失回执、存储错误、暂失宿主管理权或窗口验证失败时保留原 ID，重试不会新建第二个身份。
- 关闭弹窗不撤销已提交请求。迟到成功回执只更新身份列表，不覆盖用户更新的页面、Bot、Work 或 Task 选择；A→B→A 也视为新导航。重新打开可明确选择已创建 Bot。
- 原生模态窗口提供居中布局、名称初始焦点、Tab 焦点约束和 Esc 关闭。表单有重复提交与输入法 Enter 保护，使用现有深浅主题。

### 创建流程回归

- `test:bot-create` 覆盖严格校验、宿主身份/权限、原子回滚、并发及丢回执重试、重复名、重开数据库及原 MyBuddy/Task 保留；`test:bot-create-ui` 覆盖 27 个实际 React 事件/状态场景，包括恢复核对、迟到回执和导航竞争。输入法保护是事件级测试，不冒充真实输入法验收。
- 整合主线版本 0.1.108 后，最终 `pnpm -s typecheck` 通过；默认 `pnpm -s test:all` 为 384 项中 383 通过、1 失败。唯一失败仍为 `test:atspi-transport` 无法创建私有 D-Bus Unix socket；门禁结果如实保留失败，未更新失败基线。新增 store action 与 IPC 通道已在各自接口契约清单中明确登记，并通过检查。
- 标准 `pnpm dev` 的真实 Linux 桌面已从创建入口填写名称/职责，建立两个新 Bot，检查空对话和身份设置，再分别聊天和委托。创建不增加消息/Task/Work，普通聊天不增加 Task/Work；两个 Bot 的消息、草稿和事项独立。对另一 Bot 的精确 Work ID 发起控制被拒绝，两方事项状态/版本均未变。
- 停止并重新启动标准 dev 后，两个 Bot 的身份、对话、各自草稿及选中事项恢复；Bot/Work/Task/消息计数与重启前一致，没有重复执行。960px 深色窗口的创建弹窗、初始焦点、Shift+Tab 环绕和 Esc 关闭实测通过，原 MyBuddy 草稿、浅色外观与窗口尺寸已恢复。
- 只读对比创建前数据库：原 1 个 Bot、1 个专家版本、8 个 Work、50 条 Bot 消息与 11 个 Task 的所有原记录均未改变。两个新增验收 Work 保留待评审，均无活动执行；不把测试记录标成真实目标已完成。
- 桌面验收继续使用隔离 HOME 与本地模型夹具，不代表真实外部模型、跨设备或发行包验收。没有扩大权限、发送外部消息、打包或安装。

以下为原始页面方案与验收清单，用于保留设计边界与后续验收要求。

## 0. 用户已定的页面边界

1. **新建独立一级页面，不往现有普通 Task 对话 UI 里塞 Bot/Work 总览。**
2. **普通模式和 Bot 模式两套界面，复用共通组件与底层服务。**普通模式原有体验保留；Bot 模式针对长期 Bot 身份、持续交流与 Work 承诺单独组织界面。
3. **入口位置固定：现有左侧栏底部账户菜单中的「自动化」正上方，新增「Bot 模式」。**点击进入新的 Bot UI 页面。不是自动化的子页面，不是原来任务树中的新 Task，也不是覆盖已有「助手」页。
4. 两套页面可来回切换，原普通 Task 的选择、草稿和执行状态不被 Bot 页面覆盖；Bot 当前选择和会话草稿也单独保存。

## 1. 精确入口与路由

```text
  自动化         // 原页保留：现有规则管理

```

- [src/renderer/src/types.ts](../src/renderer/src/types.ts)：`Page` 联合类型新增 `"bot"`，保留 `"chat"`、`"assistant"`、`"automation"` 等旧值不变。

- 账户菜单继续作为所有页面的统一导航；Bot 页面内另有「返回普通模式」入口（`setPage("chat")`，恢复上次普通 Task 或普通首页）。点击菜单中的其他现有入口也正常退出 Bot 页面。

## 2. 两套页面的外观与职责

```text
普通模式（现有）
┌──────────────────┬──────────────────────────┬────────────────────┐
│ 普通 Sidebar     │ Task ChatView            │ ArtifactPanel      │
│ 新建任务          │ Task 消息和执行            │ 成果/浏览器/终端    │
│ 独立任务          │ 项目/Goal/工具             │                    │
│ 工作空间          │                          │                    │
└──────────────────┴──────────────────────────┴────────────────────┘

Bot 模式（独立）
┌──────────────────┬──────────────────────────┬────────────────────┐
│ Bot 导航          │ Bot 长期对话              │ Work 详情          │
│ Bot 身份列表      │ 与普通交流不冲突            │ 目标/责任/状态      │
│ 该 Bot 的 Work   │ 事项引用/成果/待决卡片       │ 成果/验收/下一步    │
│ 进行中/待确认     │ Bot Composer             │ 可展开执行证据      │
└──────────────────┴──────────────────────────┴────────────────────┘
```

**左列：**选 Bot 身份，而不是选 Task。显示 Bot 名称、在线/离线可核实状态、目前负责的 Work、需要用户处理的事项。切换 Bot 只换 Bot 上下文。Bot 的专家配置是能力标签，不把专家、worker/subagent 伪装为必须长期存在的独立 Bot。

**中列：**用户直接和当前 Bot 长期交流；普通问答不必创建 Work。Bot 接受委托之后插入有稳定 ID 的 Work 卡片，摘要展示“目标、当前负责人、已确认进展、下一步、需要用户决定什么”；相同对话可关联多个 Work，点击具体卡片确定目标 Work。Bot 持续负责，后台执行不阻塞前台聊天。

**右列：**选择 Work 时打开 `WorkInspector`。默认呈现「概览 / 成果与验收 / 历史与执行」三级内容：目标与模式 once/watch、责任、是否暂停/结算、验收缺口、当前要求/来源版本、证据、交接、订阅。高级详情可打开关联 Task、Durable 执行、子代理、诊断与用量，不把内部进度平铺在主对话。未选 Work 时显示 Bot 的职责/待办概览，不假造活跃任务。右列可以折叠；窄窗口改为抽屉，手机使用 Bot 列表→对话→Work 详情下钻。

**跨模式公共区域：**沿用当前品牌、账户菜单、设置和统一系统通知。可以复用 `Sidebar` 的外层、头部和账户菜单，但在 `page === "bot"` 时必须**替换普通的「新建任务/独立任务/工作空间」侧栏内容**为 Bot 专用导航；不能让普通 Task 树与 Bot Work 列表同时挤占同一左栏。恢复普通页面时原有 Task 侧栏原样呈现。

## 3. 复用边界：视图分离，基础能力共享

| 对象 | 普通页面 | Bot 页面 | 复用要求 |
| --- | --- | --- | --- |
| 导航与布局 | 现有 Sidebar/ChatView/ArtifactPanel | BotNavigation/BotConversation/WorkInspector | 共用 App shell、账户导航、可调整面板基础组件；不共用整个页面 DOM |
| 消息 | Task 对话 | Bot 对话 + Work 引用 | 抽取并复用 MessageItem、Markdown、附件展示、工具/成果卡片等纯渲染能力 |
| 输入 | 现有 Task ChatInput | Bot 专属 Composer | 共用输入基础控件与附件/引用功能，分别接入 Task 发送命令与 Bot 消息/Work 控制入口 |
| 专家与工具 | Task 专家/能力选择 | Bot 配置与执行时快照 | 复用 ExpertService、工具、权限、项目/工作区及文件操作能力；配置绑定对象不同 |
| 后台 | Task/Pi 直接执行 | Work→ExecutionBinding→Pi Durable | 执行内核、子代理、checkpoint 与恢复只保留一套，Work 增加业务调度/责任层 |
| 成果查看 | 已有 ArtifactPanel | Work 关联成果/证据 | 抽取文件、浏览器、终端和产物的通用 Viewer；Bot 面板按 Work 的授权和来源定位 |
| 状态 | `activeTaskId` 与 Task store | `activeBotId`/`selectedWorkId` 的独立 UI 选择 | 不借用 Task ID 充当 Bot/Work ID；权威事实来自 Work 服务的持久投影 |

注意：当前 `ChatInput.tsx` 直接依赖 `activeTaskId`、Task 草稿及 Task 发送路径；`ArtifactPanel.tsx` 同样依赖 Task 活动态。**不应只 import 旧组件并传假 `taskId` 来假装复用。**提取合适的纯输入/渲染/查看子组件和公共 hooks，再分别由普通模式与 Bot 模式的容器调用；不要复制两份完整的消息/输入实现，也不破坏普通模式现有功能。

## 4. 数据流与核心交互

1. 用户从账户菜单点「Bot 模式」→ `setPage("bot")` → `BotWorkspacePage` 渲染；左侧 Bot 导航在 Bot UI 内显示。路由仅切换展示，不创建 Task、不触发 Durable submit。
2. 选择一个 Bot → 读取持久 `botId` 映射的身份、渠道会话与未完成 Work。未查到 Bot/无法连接时给出真实空态或离线态，不回退成伪造的活跃 Task。
3. 用户发送普通问题 → Bot 消息入口；用户委托/改变目标/暂停等 → 经可信宿主创建或控制目标 `workId`，完成受理后在对话显示事实卡片。多个 Work 有歧义时用选中 Work/卡片引用消歧。
4. 单击 Work 卡片/左栏 Work 条目 → 更新 `selectedWorkId`，右侧展示唯一 Work 真源的投影。执行/日志只作为可展开的关联对象。
5. 通知/成果/验收数据经统一 Work 服务投影并按版本排序；重放历史回执不能广播旧 UI 状态。实际的离线、未知副作用、写入被阻止、待 Omarchy 实测都必须如实呈现。
6. 返回普通模式 → 恢复原来的 `activeTaskId`、普通页面右侧面板及输入草稿；再次进入 Bot 模式 → 恢复原来的 Bot/Work 选择及安全保存的输入草稿。模式间不得交叉发送和展示错误上下文。
7. 其他一级页面（项目、自动化、插件、设置等）仍为现有公共入口，不因为 Bot 页面存在而复制一套。

## Work 团队入口

Bot 模式顶栏的「组队开工」可选择一个负责人和多名成员，明确目标、工作区、逐人分工、验收条件与共享预算。成员使用独立 Bot 身份和 Durable 执行记录，按顺序工作，负责人随后只读汇总。事项在负责人和参与成员的列表中可见，成员讨论权限不等于负责人控制权。

团队模板只保存成员与分工，不保存授权或启动工作。当前执行范围是用户选择的目录内可核对的文件操作，不包含不透明 shell、外部连接或桌面控制。修改要求后的显式重新安排仅做只读复核，历史成果不会自动通过新验收。详见 [团队使用方式与恢复边界](bot-work-team-ui.md)。
