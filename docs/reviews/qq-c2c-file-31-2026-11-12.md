- [media.ts](https://github.com/tencent-connect/qqbot-nodejs/blob/429a0f1b798f3b0fcef3679e207dbc0469a1df2d/src/protocol/api/media.ts): base64 `file_data`, `file_type: 4`, `file_name`, `srv_send_msg: false`; then `msg_type: 7` with `media.file_info`, `content`, original `msg_id`, reserved `msg_seq`.

## Change and boundaries

C2C accepts one frozen, hash-verified file plus summary in one media message. One existing immutable notification effect reserves one reply slot; no ledger/schema changes, public URLs, separate caption sends or untracked extra sequence numbers. Upload success is not delivery. Authority, cancellation, route/account and reply window are rechecked after upload. Missing message ID/transport failure remains unknown and is not automatically resent. Successful final receipt records both file hash and media-content request receipt.

Multiple files and QQ group files are explicitly rejected before upload/send; no silent first-file selection. Zero-length, invalid name, >10 MiB and hash-mismatched files are rejected. C2C delivery context advertises the bounded single-file capability; group remains unsupported. Existing text-only path is retained.

## Follow-up: explicit archive and official group route

The initial single-file restriction above is superseded by this follow-up, based on the same official SDK SHA. `src/protocol/api/routes.ts` supports `/v2/groups/{targetId}/files` and messages, while `media.ts` accepts the FILE enum with either C2C or group scope. We found no official blanket group-FILE prohibition in this version. This is protocol support, **not evidence of this user's group permissions or successful real group delivery**. Provider rejection remains an honest non-success, without automatic retry.

For multiple frozen files, the adapter sends **one explicitly labelled ZIP**, not several original file messages. It includes each exact original byte sequence under a unique numbered path plus `manifest.json` with original names, SHA-256, lengths and summary. Duplicate filenames are preserved without overwrite. Fixed ZIP metadata and STORE encoding make the wrapper repeatable; its hash is recorded beside each original-file receipt. Single files remain unwrapped. Existing 10 MiB per original and 20 MiB total limits remain; at most 128 files and a final archive <=20 MiB are accepted. Too-large archives fail before upload. This uses existing JSZip, adds no public file hosting or extra reply slot, and does not change the delivery ledger schema.

Additional current-source tests passed: exact ZIP contents/manifest/hashes, duplicate names, identical frozen input produces identical archive, explicit recipient-visible archive notice, group URL/method/slot shape, and real SQLite two-file notification drains only one upload/send and reopens with both file receipts. Existing cancellation, changed revision, expired reply, malformed/lost receipt and tampering cases remain in the QQ suite. DingTalk and Discord synthetic gateway suites also pass on the preceding a4a42e1d baseline; these are not real account acceptance.

Real QQ group/C2C receiver rendering and opening, real DingTalk/Discord accounts, and a genuinely independent always-online host remain unverified. No messages were sent to real QQ users/groups in this work.
