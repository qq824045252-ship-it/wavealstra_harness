# Work 摘要分页与按需详情

## 变更

- 事项列表改为 SQLite 服务端查询，每页默认 24 条。个人 Bot、指定团队、临时/历史团队、回收站与全局范围均由主机按当前用户约束；搜索、状态筛选、排序、总数、各视图计数与当前页属于同一事务快照。
- 初始同步只返回 24 条摘要。增量同步与实时推送也只发送摘要；摘要有明确的 `listSummary` 标识，完整成果、执行、协作与原委托仍由 `getWork` 单事项读取。渲染端全局摘要缓存最多保留 100 条，不作为完整列表或授权依据。
- 页面使用稳定的更新时间/work ID 排序。页面重新查询时替换当前页；跨页加载检查 epoch、sequence 和数据库 revision，避免删除、插入、移动或外部连接写入造成混合快照。晚返回不能覆盖新 Bot、团队、关键词或页码。
- 16 页有界缓存仅保存摘要，按用户、查询、在线状态及 SQLite 本连接/外部连接变更失效。事务中不复用缓存；返回克隆，避免污染。搜索防抖 250ms，未变化的轮询不重复扫描。可见列表与打开的详情每 5 秒补读，补足不经过投影日志的关联事实变更；隐藏列表停止轮询。
- 完整目标、验收条件、原有下一步、成果正文与文件路径仍可搜索，保留 NFKC/大小写归一化。卡片只取 accepted/proposed 成果摘录，拒绝成果不会冒充进展。列表显示状态与详情的状态规则做对照回归。
- 详情读取独立于列表缓存。未加载的旧事项可按 ID 打开，读中立即显示可返回的外壳；旧响应、删除与普通团队视图中的已移除事项不能复活。返回保留来源、页码、筛选、滚动和焦点，临时/历史团队不创建新团队身份。
- “所有消息”、历史团队入口及回收站同步改为摘要分页，移除其全量详情旁路。活动面板仅查询已有候选任务 ID 的绑定关系，每次最多 500 个，不传输整个执行历史。
- 旧远端协议仍保留完整初始快照，避免旧客户端只能看到 24 项；本次没有宣称手机旧协议完成分页改造。
- 没有更改数据库 schema 版本，没有清库、丢弃历史、构建发行包或安装产品。

## 大数据结果与限制

5 万行持久 SQLite，另有 200 份约 72KB 的报告：每页 24 条约 18–30KB，完整详情投影调用为 0。普通列表冷读约 0.26 秒，缓存命中约 0.4–0.6ms；保留全部原搜索语义的冷全文搜索约 1.7–2.1 秒，缓存命中约 0.5–0.6ms。

冷全文搜索仍在主进程同步执行，极大数据集首次搜索可明显停顿。这是保留的性能边界，不用热缓存数字掩盖；可继续做异步查询或增量搜索索引。当前实现解决了初始/每页全量详情传输与展开问题，并未宣称所有查询恒定耗时。

`test:bot-work-phase5-native-story` 在 stageOne 的 `must-not-write` 断言上失败（actual 1，expected 0）。已用 `git archive 77d0d59` 的独立原始副本同命令重现相同位置、相同结果，确认不是本次分页新增；未修改失败基线。未运行机械全量 `test:all`、完整故障注入、打包或 Windows 验收。
