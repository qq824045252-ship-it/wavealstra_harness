# Browser collection integration

`BrowserCollection` accumulates the rows returned by caller-owned snapshots, preserving first-seen order and one-based `sourceStep`. The root adapter owns locators, trusted navigation/scroll input, UI leases and per-await page validation; the module does not expose arbitrary page JavaScript. Snapshots must provide a stable unique key and stable cell values; optional `index` is the zero-based dataset index, never the currently rendered slot. `queryIdentity` should identify active filter/sort and remain stable across pages. Supply `expectedRows` only when a trustworthy count is actually observed. A `terminal: true` must mean positive terminal evidence (e.g. observed end marker or disabled next control), not merely idle time or no newly rendered rows.

```ts
const engine = new BrowserCollection(); // retain across tool calls
const result = await engine.collect({
  identity: { owner, tab, document, query }, // generated by the host, not page/tool input
  source: { snapshot, advance }, scope,
  budget: { maxSteps: 10, maxRows: 1000 }, cursor // omit cursor for first call
});
```

`maxSteps` bounds snapshots in this call; `maxRows` bounds the total retained rows. The shared `AutomationScope` supplies the deadline, cancellation and host validation. An advance can dispatch a side effect: the module calls `scope.dispatch()` first. Root must ensure in-flight native operations drain before releasing any shared input lease, including after timeout, and must not blindly replay a failed advance. A failed or cancelled call invalidates its cursor because advance may have taken effect. A cursor is opaque, in-memory, single-flight and bound to exact owner/tab/document/query; the host must verify current identity on each call and expire/discard on lifecycle changes. Registry is bounded (default 64 continuations, 15-minute idle TTL); `discard(cursor, identity)` frees one.

Only `terminal:true` after consistency checks reports `complete`: all observed keys must have stable cells and indices, expected count must match if supplied, and indexed rows must form an unbroken zero-based sequence. An explicit terminal signal remains an assertion supplied by the adapter; this algorithm cannot prove that a misleading website actually exposed every row. `partial` reasons distinguish budget, no-progress, missing terminal evidence, changed query/count, key/index conflict, count mismatch and index gaps. Budget/no-progress/no-terminal expose a cursor; changed/conflicting/inconsistent results cannot resume. A cursor from a budget-limited partially consumed snapshot rereads that same snapshot before advancing, so no rows are skipped.

Validation: `pnpm exec electron scripts/browser-collection-electron-test.ts`, with `ELECTRON_RUN_AS_NODE` unset, passed using an isolated profile and a real Electron DOM fixture. It exercises real scroll events with recycled visible rows, paginated pages, growing infinite content, literal expected five-row results, budget continuation and row cap, foreign-tab cursor rejection, stall, missing terminal, observed count mismatch, filter change and conflicting repeated key. The fixture uses DOM callbacks, not the registered `browser_exec` bridge or native user input; those remain integration work. `pnpm exec tsc --noEmit -p tsconfig.node.json` filtered to the module reported no module errors; this is not a repository-wide typecheck claim.
