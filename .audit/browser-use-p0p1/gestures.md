# Browser gestures integration

`BrowserGestures.ts` is a small set of helpers, not a second browser or debugger owner. The caller must resolve and revalidate its task-owned observed target, map nested-frame coordinates into the root viewport, hold the existing page presentation/input lease throughout the operation and cleanup, and pass the existing `AutomationScope`. The helpers conservatively mark dispatch before effects; a completed transport call does not establish a business outcome. Never blindly replay an action after dispatch with unknown effect.

- `pointerDrag(input, scope, points)` accepts 2–64 bounded finite viewport points. It sends trusted pointer input and supplies Electron's `leftbuttondown` modifier for drag movement. The browser input adapter **must** translate that modifier to CDP `buttons: 1`. On cancellation/failure it drains any in-flight input and releases only its own left button; keep the lease until the helper settles. A cleanup failure is propagated.
- `htmlDrag(protocol, scope, points, {items, dragOperationsMask})` sends CDP dragEnter, dragOver, and drop with bounded explicit MIME/data items, or dragCancel on interrupted in-progress drag. It models a supplied data payload; it does not fire a source element's `dragstart` and must not be presented as a complete native source-to-destination drag. It uses the existing inspector `protocolCommand`, not another debugger. Nested frame data routing is not established by this test.
- `insertTextSequential(input, scope, text, delayMs?)` uses trusted insertText once per Unicode code point, no clipboard, with bounded length/delay and a shared deadline. This is text insertion, not physical key events or grapheme segmentation.
- `setDateInput(scope, evaluateOnElement, type, value)` sends a generated function expression to the supplied evaluator, which must bind it to the already observed, validated target. It requires an exact native date/time/month/week input type, editable element, valid exact value and matching readback. It uses the native value setter and dispatches synthetic `input`/`change`; return strategy is `synthetic-setter`. Framework code must not report those events as trusted key input. The check and mutation occur in one evaluator invocation; parent must preserve node identity, frame and navigation guards.

Validation: with `ELECTRON_RUN_AS_NODE` unset, `pnpm exec electron scripts/browser-gestures-electron-test.ts` passed on a real isolated Electron WebContents and existing attached debugger. The test verified trusted down/move/up with left-button state; real trusted HTML drop with exact Unicode payload; cancellation releases the owned button; sequential Chinese/emoji input; native date value plus explicitly untrusted synthetic input/change; invalid date rejected. The test uses a small direct CDP input adapter and loads the actual `AutomationScope` with an in-memory esbuild transform, so it does not prove the production `BrowserNativeInput` adapter or registered tool bridge. Typechecking with `pnpm exec tsc --noEmit -p tsconfig.node.json` filtered to this module produced no module diagnostics; this is not a full-gate claim. BrowserNativeInput currently needs the `leftbuttondown` to CDP buttons mapping, communicated to the integrator.

References: [CDP Input.dispatchDragEvent](https://chromedevtools.github.io/devtools-protocol/tot/Input/#method-dispatchDragEvent), [MDN input event](https://developer.mozilla.org/en-US/docs/Web/API/Element/input_event).
